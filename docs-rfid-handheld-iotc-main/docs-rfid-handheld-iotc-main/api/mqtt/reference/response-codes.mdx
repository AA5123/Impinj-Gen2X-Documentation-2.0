## Overview

Every reply to a command carries a `response` object with a numeric `code` and a human-readable `description`. This page lists every code: what it means, why it occurs, what to do, and which commands can return it.

`code` is a closed set. Only the values in the catalog are defined, so treat any other value as an unrecognized reply and log it.

Response codes come only from the reader, inside a command reply. They are separate from the return codes that MQTT 3.1.1 defines for CONNACK and SUBACK, and from errors that your MQTT client library raises. Events never carry a response code.

The catalog and the matrix are generated from the MQTT API contract.

## How to Read a Code

Decide the outcome from `response` in this order:

- **`code` is `0`, or `code` is absent and `description` is `"Success"`:** the command succeeded. The contract requires `code`, but readers have been reported to omit it on a successful reply; error replies always include it. See [Success Without a Code](/api-reference/mqtt/protocol-reference/message-envelope#success-omits-code).
- **`code` is `1`:** the reader accepted the request and is still working on it. Only [`set_os`](/api-reference/mqtt/mgmt/set-os), [`reboot`](/api-reference/mqtt/mgmt/reboot), and [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate) return it. See [Asynchronous Commands](/api-reference/mqtt/protocol-reference/message-envelope#async-accept).
- **`code` is `101`:** a default error, returned when no more specific code applies.
- **Any other code:** the command did not succeed. Use the code's cause and recommended action in the catalog.

Don't parse `description`: its wording can change between firmware builds.

The catalog gives each code its cause and recommended action. When the fix takes more than one step, these guides walk through it:

Before you retry after an error, apply the contract's rule: retry only when the recommended action names a condition that can change without changing your request, such as waiting, stopping an inventory, or charging the reader. Otherwise change the request first. See [Duplicates and Retries](/api-reference/mqtt/protocol-reference/qos-and-delivery-semantics#idempotency).

## Notes and Caveats {#notes--caveats}

- **Codes `6` and `7`** are defined but no published command returns them. They are kept because response codes are a fixed numeric sequence, and removing one would renumber the rest.
- **Codes `31` and `32`** concern tag write length in [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode). The cause text for code `31` mentions a certificate, which does not fit a tag write; go by the code's name.
- **A command with no row-specific codes,** such as [`get_version`](/api-reference/mqtt/mgmt/get-version) or [`config_events`](/api-reference/mqtt/mgmt/config-events), returns only `0` and `101`.
- **A reply with code `1` is not a result.** Subscribe to the event topic before you send [`set_os`](/api-reference/mqtt/mgmt/set-os) or [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate), and wait for the outcome. [`reboot`](/api-reference/mqtt/mgmt/reboot) sends no outcome event.
- **No reply is not a code.** A misspelled `command` value, an oversized message, or a full command queue can produce no reply at all. See [What Happens to a Malformed Command](/api-reference/mqtt/protocol-reference/message-envelope#malformed-commands).
