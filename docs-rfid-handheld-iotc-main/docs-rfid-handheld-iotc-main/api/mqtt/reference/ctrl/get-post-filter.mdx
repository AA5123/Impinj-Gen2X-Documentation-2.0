## Overview

`get_post_filter` **reads back the reader's current post-filters** — the rules that include or exclude scanned RFID **tag data** before it is reported to a data endpoint. Each rule matches tag data by pattern (prefix, suffix, or regex) and either reports (`INCLUDE`) or drops (`EXCLUDE`) it, scoped to a data endpoint. It is read-only. It is a **control-plane ([CTRL](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)) command**; configure filters with [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter).

This is a **CTRL-endpoint command**: it is published on the **control** endpoint (`<tenantId>/CTRL/clients/cmnd/<serial>`) and answered only there (not on the [MGMT](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)/[MDM](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types) channel). Returning a response requires an **active CTRL endpoint** ([`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint), `epType: CTRL`, `activate: true`).

## When to Use

Use `get_post_filter` to **inspect the reader's post-filters**:

- **Audit filtering** — see which patterns are included/excluded per data endpoint before relying on the tag-data stream.
- **After [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter)** — verify a filter was applied (the setter's response carries no configuration echo).
- **Confirm none are set** — an absent `postFilterPayload` means no filters are configured (see [Response Semantics](#response-semantics)).

Control commands are answered **only on the CTRL endpoint** — publishing `get_post_filter` to the MGMT/MDM command topic produces no reply.

Post-filters act on **tag data** (post-singulation), distinct from the Gen2 `select` pre-filters in [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) that act on the air interface. If control commands time out, confirm a CTRL endpoint is active and activate one with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) if needed.

## Key Fields

- **`postFilterPayload.postFilter[]`** (response) — the configured rules; absent when none are set.
- **`dataEpType`** (response) — the data endpoint (`DATA_EP1` / `DATA_EP2`) each rule scopes to. `DATA_EP2` targets the [`DATA2`](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types) endpoint, which is currently not supported.
- **`matchPattern` + `matchPatternMethod`** (response) — what to match and how (`PREFIX` / `SUFFIX` / `REGEX`).
- **`reportOperation`** (response) — `INCLUDE` (report matches) or `EXCLUDE` (drop matches).
- **`response.code`** (response) — read this to determine success vs failure. The contract requires it; note the reported success-path omission (see [Success without a code](/api-reference/mqtt/protocol-reference/message-envelope#success-omits-code)). See [Response Codes](#response-codes).

## Response Semantics

- **`postFilterPayload` is absent when no filters are set.** With no post-filters configured, the device omits `postFilterPayload` entirely — not even an empty `postFilter: []`. Treat its absence as "no filters." When filters exist, `postFilter[]` lists them.

## Notes and Caveats {#notes--caveats}

- **Post-filters vs pre-filters.** `get_post_filter` reports **post-filters** — pattern rules applied to scanned **tag data** before it reaches a data endpoint (`INCLUDE`/`EXCLUDE`). These are separate from the Gen2 `select` **pre-filters** in [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode), which filter on the air interface during inventory. Configure post-filters with [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter).

`get_post_filter` is a read-only, idempotent getter — safe to poll. Use it to verify a change applied by [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter); it carries no credentials in request or response. For the concept-level view, see [Post-Filter Reported Tags](/guides/read-tags-and-barcodes/post-filter-reported-tags).
