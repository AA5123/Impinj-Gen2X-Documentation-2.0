The reader publishes three events on its own. None carries a [`requestId`](/api-reference/mqtt/protocol-reference/message-envelope#correlating-responses) or a `response`, and none names its own kind: recognize each by the members it carries.

| Event | Arrives on | QoS | Recognize it by |
| --- | --- | --- | --- |
| [`mqttConnEVT`](/api-reference/mqtt/events/mqtt-connection-event) | The endpoint's connection-state topic, [`publishTopics[2]`](/api-reference/mqtt/protocol-reference/endpoints-and-topic-slots) | 0 | `connectionState` |
| [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) | The endpoint's event topic, `publishTopics[1]` | 0 | `eventName: "heartbeat"` |
| [`alerts`](/api-reference/mqtt/events/alerts-event) | The endpoint's event topic, `publishTopics[1]` | 1 | `type`, `id`, `state` and `priority` |

`heartBeatEVT` and `alerts` are enabled with [`config_events`](/api-reference/mqtt/mgmt/config-events). Whether `mqttConnEVT` is retained is not settled; the others are not retained. Tag data, the fourth event, is under Telemetry.
