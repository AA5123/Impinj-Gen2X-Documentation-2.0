## Overview

`get_status` retrieves a point-in-time health and status snapshot of the reader. It is a read-only query on the device-management ([MGMT](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)) endpoint: the app publishes the command and the device publishes a correlated reply containing power, radio, clock, terminal-link, and battery information under `deviceStatus`.

Because it is read-only, `get_status` is safe to call at any time. It complements the asynchronous [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) push: `heartBeatEVT` carries only a lightweight inventory-status or battery-alert summary, so use the event stream for continuous monitoring and `get_status` for an immediate, full snapshot.

## When to Use

Use `get_status` when you need an **immediate, correlated snapshot of reader health** — power source, radio activity/connection, system clock, terminal link, and battery condition — typically in a management workflow over the MGMT endpoint. It confirms device state on demand rather than waiting for the next asynchronous heartbeat.

- **Get:** the current `deviceStatus` snapshot (power, radio, clock, terminal connection, battery).
- **Use it for:** pre-flight safety checks before a state-changing command, spot health checks, and diagnostics. (`deviceStatus.radioActivity` in the response reports the activity status of the device's radio — see [Key Fields](#key-fields).)
- **Prefer a different command when:** you want continuous monitoring rather than a single read — subscribe to [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) instead for periodic pushes, though it carries only an inventory-status or battery-alert summary, not the full power/radio/clock/terminal/battery snapshot `get_status` returns.

## Response Semantics

- **Which `deviceStatus` fields appear depends on device state and model** — absent fields are normal behavior, not an error. Note that `deviceStatus` reports two distinct temperatures: `deviceStatus.temperature` (device) and `deviceStatus.batteryStatus.temperature` (battery) — do not conflate them.
- **The reader has no RTC backup battery.** After a cold start or factory reset, `systemTime` starts at a baseline default; the device syncs its clock from **network time** once it has a network connection. There is currently no API to change the NTP configuration — set the NTP server details (and, if NTP is unreachable, the device time itself) from the **123RFID Desktop** application. Time-sensitive operations (TLS certificate validity, log/event timestamps) may use the default time until the clock has synced.
- **`stateOfHealth` is one grade, on two surfaces.** `deviceStatus.batteryStatus.stateOfHealth` here and the `batteryAlert.stateOfHealth` carried by [`alerts`](/api-reference/mqtt/events/alerts-event) and [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) use the **same** enum — `GOOD` / `CRITICAL` / `MODERATE` — so shared battery logic needs no conversion. Keep it distinct from the event's `status`, which is a charge band (`LOW` / `CRITICAL` / `CHARGING` / `FULL` / `HIGH`), not a health grade. See [Interpret `stateOfHealth`](/guides/operate-and-monitor/monitor-reader-health-and-battery#interpret-stateofhealth).
- **`ntp.offset` and `ntp.reach` are not reported by the reader.** The schema declares both fields; the values on the **Schema** tab (`120` and `321`) are the schema's own field examples, and the contract's message example shows `0` for each. Current firmware has been reported not to populate either one, so treat their absence as normal and do not build clock-health logic on them. Removing them from the schema is an upstream request to the API owners; until then the fields remain declared.

## Notes and Caveats {#notes--caveats}

- `get_status` is the on-demand poll; [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) and related alerts push a lighter periodic summary (an inventory-status or battery-alert block), not the full `get_status` snapshot. Prefer the events for continuous monitoring and `get_status` for a complete point-in-time check. Cross-command `apiVersion` reporting can differ (for example [`mqttConnEVT`](/api-reference/mqtt/events/mqtt-connection-event) emits a numeric `apiVersion`); that is a firmware note, not a `get_status` schema difference.
