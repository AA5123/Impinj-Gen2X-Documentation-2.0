> 📕 **REFERENCE** · **Audience:** API consumer · **Use:** add, delete, or modify a post-filter rule on the reader

## Overview

`set_post_filter` **configures a post-filter** — a rule that includes or excludes scanned RFID **tag data** before it is reported to a data endpoint. Each call operates on **one** filter, chosen by `postFilterPayload.operation` (`ADD` / `DELETE` / `MODIFY`): the rule matches tag data by pattern (prefix, suffix, or regex) and either reports (`INCLUDE`) or drops (`EXCLUDE`) it, scoped to a data endpoint. It is a state-changing **control-plane ([CTRL](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)) command**; read the current filters back with [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter).

This is a **CTRL-endpoint command**, published on the **control** endpoint (`<tenantId>/CTRL/clients/cmnd/<serial>`) and answered only there (not on the [MGMT](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)/[MDM](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types) channel). Returning a response requires an **active CTRL endpoint** ([`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint), `epType: CTRL`, `activate: true`). Also: `dataEpType` is the **enum** `DATA_EP1`/`DATA_EP2`, **not** the endpoint *name* — sending an endpoint name returns [code `23`](/api-reference/mqtt/response-codes#code-23) (see [Request Semantics](#request-semantics)).

## When to Use

Use `set_post_filter` to **control which scanned tag data reaches a data endpoint**:

- **Include only matching tags** — `reportOperation: INCLUDE` reports only tags whose data matches; everything else is dropped.
- **Exclude noisy tags** — `reportOperation: EXCLUDE` drops matching tags from reporting.
- **Match by prefix, suffix, or regex** — choose `matchPatternMethod` to fit the tag-data pattern.
- **Manage the rule set** — `ADD` to install, `DELETE` to remove, `MODIFY` to update; verify with [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter).

## Request Semantics

**Modes.** `postFilterPayload.operation` selects the action; each call handles one rule:

- **`ADD`** — install a new post-filter for the given `dataEpType`.
- **`DELETE`** — remove the post filter on a data endpoint. Send `operation: DELETE` with `dataEpType` alone; `matchPattern`, `matchPatternMethod` and `reportOperation` are not needed. Undoes a prior `ADD` on the same `dataEpType`.
- **`MODIFY`** — update an existing filter.

Confirm the resulting rule set with [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter), which returns the stored `postFilter[]` (or nothing when none remain).

- **`dataEpType` is an enum, not the endpoint name.** `dataEpType` must be the enum value `DATA_EP1` or `DATA_EP2` — **not** the endpoint *name* you gave a data endpoint in [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) (e.g. `DATA1_EP`). Sending the endpoint name is an enum violation and the device rejects it with **[code `23`](/api-reference/mqtt/response-codes#code-23)** ("Invalid enum value"). Map your [`DATA1`](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types) endpoint to `DATA_EP1` when setting a filter; `DATA_EP2` targets the `DATA2` endpoint, which is currently not supported.
- **`matchPattern` rules follow the match method.** For `PREFIX` and `SUFFIX` methods, `matchPattern` must be **hexadecimal digits only, with an even count** — the contract states this rule in the field description but does not enforce it with a pattern; for `REGEX` it is a free-form regular expression.
- **`PREFIX` post-filters and Gen2 `select` pre-filters are mutually exclusive.** A `PREFIX` post-filter precludes using Gen2 `select` pre-filters at the same time.

## Notes and Caveats {#notes--caveats}

- **Post-filters vs pre-filters.** `set_post_filter` configures **post-filters** — rules applied to scanned **tag data** before it reaches a data endpoint (`INCLUDE`/`EXCLUDE`). These are separate from the Gen2 `select` **pre-filters** in [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode), which filter on the air interface during inventory.

`set_post_filter` is **reversible** — an `ADD` is undone by a `DELETE` on the same `dataEpType`. It carries no credentials (match patterns are tag-data hex/regex strings). After setting a filter, **verify with [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter)** — the setter's response has no configuration echo. For the concept-level view, see [Post-Filter Reported Tags](/guides/read-tags-and-barcodes/post-filter-reported-tags).
