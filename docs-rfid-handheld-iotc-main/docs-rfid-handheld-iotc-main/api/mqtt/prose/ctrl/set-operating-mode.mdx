> 📕 **REFERENCE** · **Audience:** API consumer · **Use:** configure the reader's RFID operating mode

## Overview

`set_operating_mode` **configures the reader's RFID operating mode** — the profile, advanced RF configuration, tag access operations, radio start/stop triggers, the Gen2 `query`, select pre-filters, and tag-metadata reporting flags. It is a state-changing **control-plane ([CTRL](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)) command**. It is a **partial, merging** update: you send only the sub-objects you want to change and they merge into the current mode. Read the result back with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode).

**`accessOperations` arm destructive tag operations (`WRITE` / `LOCK` / `KILL`) that execute on the next inventory — `KILL` and `PERMANENT_LOCK` are irreversible.** See the danger callout in [Notes and Caveats](#notes--caveats) before sending.

This is a **CTRL-endpoint command**, published on the **control** endpoint (`<tenantId>/CTRL/clients/cmnd/<serial>`) and answered only there (not on the [MGMT](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types)/[MDM](/api-reference/mqtt/protocol-reference/connection-and-session#endpoint-types) channel). This **requires an active CTRL endpoint** ([`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint), `epType: CTRL`, `activate: true`); without one, you get no response.

**Set the [regulatory region](/api-reference/mqtt/mgmt/get-current-region) first.** Before you start an RFID inventory, make sure the reader’s regulatory region is configured: the reader does not transmit until it is, and the region is set outside MQTT with 123RFID Desktop or 123RFID Mobile. Use [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region) to verify the current region.

## When to Use

Use `set_operating_mode` to **configure how the reader reads (and acts on) tags**:

- **Select a profile** — `CYCLE_COUNT` (read as many unique tags as possible), `DENSE_READERS` (multiple readers in proximity), `OPTIMAL_BATTERY` (best battery life), `BALANCED_PERFORMANCE` (default; balances performance and battery life), or `ADVANCED` (custom link-profile settings via `advancedConfigurations`). `FAST_READ` (maximum read speed within short range) is enumerated but not currently supported.
- **Tune the radio** — transmit power, link profile, session, dynamic power (ADVANCED).
- **Compose triggers** — `radioStartConditions` / `radioStopConditions` (trigger, delay, tag/time/cycle stops).
- **Shape inventory** — Gen2 `query` and up to 32 `select` pre-filters.
- **Choose reporting** — `tagMetaDataToEnable` flags.
- **Arm tag operations** — `accessOperations` (READ/WRITE/ACCESS/LOCK/KILL) that run on the next inventory. Handle with care (see the danger note).

## Topic Mapping

| Message | Direction | Topic | Note |
| --- | --- | --- | --- |
| Request | App → Reader | `<tenantId>/CTRL/clients/cmnd/<serial>` | On the **control** endpoint. Requires an **active CTRL endpoint**. |
| Response | Reader → App | `<tenantId>/CTRL/clients/resp/<serial>` | Correlated reply; the in-payload `requestId` links the twin topics. |

Topics follow the pattern `<tenantId>/<topic>/<serial>` — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example `RFD40-212735201D0053`). `App → Reader` means your app publishes and the reader subscribes; `Reader → App` means the reader publishes and your app subscribes.

Control commands are answered **only on the CTRL endpoint**.

If control commands time out, confirm a CTRL endpoint is active ([`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) → `activeEndpoints`) and activate one with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) if needed. The mode cannot be changed while an inventory is running ([code `11`](/api-reference/mqtt/response-codes#code-11)).

See [Topics and Channels](/api-reference/mqtt/protocol-reference/topic-structure).

## Key Fields

- **`operatingModes.profiles`** (request) — the RF profile; `ADVANCED` requires `advancedConfigurations`. `FAST_READ` is the first member of the enum but is not currently supported, and data events are not supported while the sled is in it.
- **`operatingModes.accessOperations`** (request) — ⚠️ armed tag operations (destructive; see the danger note).
- **`operatingModes.select`** (request) — up to 32 Gen2 pre-filters.
- **`operatingModes.query` / `radioStartConditions` / `radioStopConditions`** (request) — inventory shaping and trigger semantics.
- **`operatingModes.tagMetaDataToEnable`** (request) — which metadata fields the reader reports on each read. The switch-to-field mapping is on [`dataEVT`](/api-reference/mqtt/data/tag-data-event#field-support).
- **`response.code`** (response) — read this to determine success vs failure; the contract requires it; note the reported success-path omission (see [Response Payload](#response-payload)) and the partial-apply-on-error behavior (see [Request Semantics](#request-semantics)). See [Response Codes](#response-codes).

## Request Semantics

**Merge.** `set_operating_mode` is **cumulative**: it updates only the aspects present in the payload and leaves all others intact — it is **not** a full replacement. For example, sending only `radioStartConditions` changes the triggers while preserving `profiles`, `query`, `select`, `accessOperations`, and `tagMetaDataToEnable`. Send `{profiles: "BALANCED_PERFORMANCE"}` alone to reset the profile without touching anything else. Because merges accumulate, **armed `accessOperations` persist** across later partial sets until you overwrite them or reboot. Confirm the resulting merged mode with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode).

- **The singular `operatingMode` wrapper around the plural `operatingModes` object is the schema-defined shape.** The command's `operatingMode` property carries a wrapper holding exactly one member, `operatingModes`, and every worked example nests it that way — the double nesting is intentional and unique to this command (see the [Glossary](/resources/glossary)). The contract marks neither level `required` and does not forbid unrecognized properties, so a flattened or renamed payload still validates — but it does not carry the operating mode where the schema defines it. Send the nested shape exactly as shown.
- **An error response can leave the mode partially applied.** An error response (e.g. `101` "Error in processing command") can leave the mode **partially applied** — always verify the result with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode) rather than assuming a `101` changed nothing.
- **`ADVANCED` requires `advancedConfigurations`; limits are enforced.** `profiles: ADVANCED` without `advancedConfigurations` returns [code `22`](/api-reference/mqtt/response-codes#code-22). `select` supports up to 32 pre-filters ([code `24`](/api-reference/mqtt/response-codes#code-24) if exceeded); an overlong `select.tagPattern` returns `28`; WRITE `data` that is too large or mismatched returns `31` / `32`. `FAST_READ` is enumerated but **not currently supported**, and configuring `FAST_READ` disables data events.

## Notes and Caveats {#notes--caveats}

:::caution[Armed access operations execute on the next inventory — and the payload carries their password]
`accessOperations` (`WRITE`, `LOCK`, `KILL`) are stored by `set_operating_mode` and executed against tags **on the next inventory START** — not immediately. `KILL` permanently disables a tag; `LOCK` with `PERMANENT_LOCK`/`PERMANENT_UNLOCK` is irreversible; `WRITE` overwrites tag memory. Because partial sets **merge**, armed operations persist until you **overwrite the `accessOperations` array** (with a benign or empty set) or [`reboot`](/api-reference/mqtt/mgmt/reboot). A profile-only set — or any partial set that omits `accessOperations` — does **not** clear them. Do this before running an inventory that should not trigger them. Each armed operation also carries `accessOperations[].config.password`, an 8-hex-char (32-bit) access/lock/kill password you send (default `00000000`) — mask it in shared artifacts. The device stores it but never echoes it back ([`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode) returns it empty). This command carries no broker/Wi-Fi credentials.
:::

- **Volatile and CTRL-only.** The operating mode resets to default on [`reboot`](/api-reference/mqtt/mgmt/reboot), and the command is answered only on the CTRL endpoint (see [Topic Mapping](#topic-mapping)).
- **`FAST_READ` is enumerated but not currently supported.** `FAST_READ` is the first member of the `profiles` enum, and the schema glosses it as "Configures the radio for maximum read speed within short range. (Currently not supported)". The command description repeats the restriction and extends it to the event plane: "When RFD40/90 sled is configured to FAST_READ profile, data events are not currently supported. On reboot the set configurations will be lost and the device will go back to default operating mode." Treat `FAST_READ` as unavailable, and expect no [`dataEVT`](/api-reference/mqtt/data/tag-data-event) traffic while the sled is in that profile.

Configure with `set_operating_mode`, then **verify with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode)** (especially after a `101`), and run the inventory with [`control_operation`](/api-reference/mqtt/ctrl/control-operation). For the concept-level view, see [Choose an Operating Mode](/guides/read-tags-and-barcodes/choose-a-performance-profile#choose-an-operating-mode).
