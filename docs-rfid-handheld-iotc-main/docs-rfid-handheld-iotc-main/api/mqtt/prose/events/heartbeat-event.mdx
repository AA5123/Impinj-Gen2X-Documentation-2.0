> 📕 **REFERENCE** · **Audience:** API consumer · **Use:** interpret the reader's periodic heartbeat event

## Overview

`heartBeatEVT` is a **device-emitted** event — the reader publishes it on its own, with **no command triggering it**, to signal that it is alive and to report basic health: uptime, an event sequence number, and optional **inventory** and **battery** sub-payloads. It is read-only telemetry and carries no credentials.

You **enable** a heartbeat rather than requesting it. The reader publishes `heartBeatEVT` at the interval you set in `heartbeatConfiguration` once the heartbeat is enabled with [`config_events`](/api-reference/mqtt/mgmt/config-events) (see [Event Semantics](#event-semantics)).

The reader publishes `heartBeatEVT` at the configured interval (at most 65,535 seconds) while the heartbeat is enabled with [`config_events`](/api-reference/mqtt/mgmt/config-events); a reboot applies the setting. Monitoring can rely on it as its primary liveness signal: when `heartBeatEVT` stops arriving, the reader, its session, or the path to your application needs attention. `heartBeatEVT` is published at [QoS 0](/api-reference/mqtt/protocol-reference/qos-and-delivery-semantics#qos), so the MQTT layer does not resend one lost in transit. Choose how many missed intervals your application treats as an outage.

## When to Use

Subscribe to `heartBeatEVT` when you want **continuous, pushed telemetry of reader liveness and health** — uptime, an event sequence number, and optional inventory and battery status — rather than polling for it on demand. It is the asynchronous twin of [`get_status`](/api-reference/mqtt/mgmt/get-status) (heartBeatEVT ↔ get_status): the heartbeat *pushes* health at a fixed interval, while `get_status` *pulls* a correlated snapshot when you ask.

- **Receive:** periodic `heartBeatEVT` payloads on the management event topic once the heartbeat is enabled and the reader has rebooted.
- **Use it for:** liveness monitoring (the *absence* of an expected heartbeat is itself a signal), tracking RFID inventory progression, and routine battery monitoring — without issuing a command per check.
- **Prefer a different call when:** you need an immediate, on-demand reading — call [`get_status`](/api-reference/mqtt/mgmt/get-status) instead. It returns a synchronous device-health and battery snapshot in a correlated response (note it does not include the heartbeat's inventory scan counts or uptime).

## Topic Mapping

`heartBeatEVT` is device-emitted and flows on the **management event topic** — it has no `cmnd`/`resp` topics of its own because no command produces it.

| Message | Direction | Topic | Note |
| --- | --- | --- | --- |
| Event | Reader → App | `<tenantId>/MGMT/clients/event/<serial>` | Published on the management endpoint's event topic. |

Topics follow the pattern `<tenantId>/<topic>/<serial>` — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example `RFD40-212735201D0053`). `App → Reader` means your app publishes and the reader subscribes; `Reader → App` means the reader publishes and your app subscribes.

The event arrives on the same management-event plane you enabled it on with [`config_events`](/api-reference/mqtt/mgmt/config-events).

See [Topics and Channels](/api-reference/mqtt/protocol-reference/topic-structure).

## Key Fields

- **`eventName`** (event) — names the event; the fixed value `heartbeat`. Required.
- **`timestamp`** (event) — ISO-8601 time the heartbeat was generated. Required.
- **`eventNumber`** (event) — a unique identifier or sequence number for the event. The schema does not guarantee it is monotonic or contiguous, so a gap between consecutive heartbeats is not necessarily a missed heartbeat. Required.
- **`data.inventoryStatus`** (event) — RFID scan state (`rfidStatus`), plus `tagCount` and `scanCount`. Present when `heartbeatConfiguration.inventoryStatus` is `true`.
- **`data.batteryAlert`** (event) — battery `status`, `stateOfHealth`, and `chargePercentage`. Present when `heartbeatConfiguration.batteryStatus` is `true`.
- **`heartbeat`** (request) — the gate flag in [`config_events`](/api-reference/mqtt/mgmt/config-events); the heartbeat publishes only once `heartbeat: true` and `heartbeatConfiguration.interval` is set (at most 65,535 seconds) (see [Event Semantics](#event-semantics)).

In the examples, `data` nests its sub-payloads, and a heartbeat may carry **one, both, or neither** of `inventoryStatus` and `batteryAlert` (the schema declares a flatter shape — see [Field Support](#field-support)). The `heartbeatConfiguration` inclusion flags you set when enabling the heartbeat control which ones appear:

- **`inventoryStatus`** — RFID scan state (`rfidStatus`), plus `tagCount` and `scanCount`. Present when `heartbeatConfiguration.inventoryStatus` is `true`.
- **`batteryAlert`** — battery `status`, `stateOfHealth`, and `chargePercentage`. Present when `heartbeatConfiguration.batteryStatus` is `true`.

## Event Semantics

### Emission

Enable the heartbeat with [`config_events`](/api-reference/mqtt/mgmt/config-events) under `eventConfiguration`: set `heartbeat` to `true` and `heartbeatConfiguration.interval` to a value of at most 65,535 seconds. The contract documents no default for either. After the reader has rebooted, it publishes `heartBeatEVT` every `heartbeatConfiguration.interval` seconds on the management event topic.

| Field | Type | Meaning |
| --- | --- | --- |
| `heartbeat` | boolean | Set `true` to enable the heartbeat stream. |
| `heartbeatConfiguration.interval` | integer (seconds) | Seconds between heartbeats. Lower = more telemetry, higher battery cost. |

<JsonBlock title="Enable the heartbeat via config_events" data={CONFIG_JSON} />

`config_events` **stores** the heartbeat configuration immediately (confirm it with [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config)), but the reader begins **emitting** only after a [`reboot`](/api-reference/mqtt/mgmt/reboot). Also note `heartbeatConfiguration` appears in a `get_endpoint_config` read only after `config_events` sets it — it is absent from a default read. See [`config_events`](/api-reference/mqtt/mgmt/config-events) for the full enable workflow.

- **If no heartbeat arrives.** Read the endpoint configuration with [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) and confirm `heartbeat: true` and an `interval` of at most 65,535. Confirm that the reader has rebooted since you sent `config_events`, and that you subscribed to the management event topic; a heartbeat published before your subscription is active is not delivered later.

### Shaping

The `heartbeatConfiguration` inclusion flags shape each heartbeat's optional `data` object — they select which sub-payloads a heartbeat carries, independently of the enabling above.

| Field | Type | Meaning |
| --- | --- | --- |
| `heartbeatConfiguration.inventoryStatus` | boolean | Include the `data.inventoryStatus` block in each heartbeat. |
| `heartbeatConfiguration.batteryStatus` | boolean | Include the `data.batteryAlert` block in each heartbeat. |
| `heartbeatConfiguration.userApps` | boolean | Declared for a `data.userApps` block. Not supported: firmware does not implement user-application status, so no heartbeat carries it. |

Because every member of `data` is optional, a heartbeat carries one, both, or neither of `inventoryStatus` and `batteryAlert`, depending on these flags. Set them alongside the enable flags via [`config_events`](/api-reference/mqtt/mgmt/config-events).

### Field Support

- **The schema and the example disagree on the shape of `data`.** The schema declares `data` as `anyOf` two flat objects — `rfidStatus` / `tagCount` / `scanCount`, or `status` / `stateOfHealth` / `chargePercentage` — so those fields would sit directly under `data`. The contract's own example, like every example on this page, nests them as `data.inventoryStatus` and `data.batteryAlert`; it validates only because neither branch forbids extra keys. Parse the nested form shown here, and tolerate the flat form.
- **`stateOfHealth` is not a charge band.** `batteryAlert.stateOfHealth` is enumerated `GOOD` / `CRITICAL` / `MODERATE`. `FULL` is a value of `status`, not of `stateOfHealth`, so a payload carrying `stateOfHealth: "FULL"` is outside the enum. Trust the enum.
- **`batteryAlert.stateOfHealth` is the same health grade as [`get_status`](/api-reference/mqtt/mgmt/get-status).** The value set here is `GOOD` / `CRITICAL` / `MODERATE`, and [`get_status`](/api-reference/mqtt/mgmt/get-status) reports `deviceStatus.batteryStatus.stateOfHealth` from that same enum. One grade, so nothing needs translating when you share battery logic between the heartbeat and the command. The battery's charge state is the separate `status` field. See [Interpret `stateOfHealth`](/guides/operate-and-monitor/monitor-reader-health-and-battery#interpret-stateofhealth).
- **Required fields and `upTime`.** `eventName`, `timestamp`, and `eventNumber` are required; `upTime` and `data` are optional. `upTime` is a **free-form string** (e.g. `"5 days 4hr 3min"`), not a machine-parseable duration — do not parse it as a number.

## Notes and Caveats {#notes--caveats}

- **No response envelope.** `heartBeatEVT` is a device-emitted event, so it carries **no `response`/`code`** — the command response-code table does not apply. No response code is defined for any event.

`heartBeatEVT` is **read-only telemetry** and carries no credentials. Use it for liveness checks (the *absence* of expected heartbeats is itself a signal), inventory progression, and routine battery monitoring.
