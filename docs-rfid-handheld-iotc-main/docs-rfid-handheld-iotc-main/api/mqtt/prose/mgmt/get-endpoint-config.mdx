> 📕 **REFERENCE** · **Audience:** API consumer · **Use:** read back the reader's MQTT endpoint configuration and saved endpoint names

## Overview

`get_endpoint_config` **reads back the reader's MQTT endpoint configuration** — a faithful view of what was provisioned with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint). It has two modes, chosen by whether you send `endpointDetails.endpointName`:

- **All-endpoints (omit `endpointDetails`):** returns every **active** endpoint's full configuration under `endpointResponse.activeEndpoints.epConfig[]`, **plus** the names of **all saved** endpoints under `endpointResponse.savedEndpoints.epNames[]`.
- **Single-endpoint (send `endpointDetails.endpointName`):** returns just that one endpoint's configuration.

It is a read-only command on the device-management (MGMT) endpoint.

**The response includes broker credentials** (`mqttParams.password`, and `username` where set) — treat it as sensitive. See the warning in [Notes and Caveats](#notes--caveats). The examples on this page are the contract's, and carry placeholders rather than real credentials.

## When to Use

Use `get_endpoint_config` to **inspect or audit** the reader's MQTT wiring:

- **Before [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint)** — review the current configuration so you do not overwrite an active endpoint unexpectedly.
- **Confirm the plumbing** — check `url` / `port`, `protocol`, `verificationType`, and the [`publishTopics`](/api-reference/mqtt/protocol-reference/endpoints-and-topic-slots) / `subscribeTopics` a broker will see.
- **List saved endpoints** — read `savedEndpoints.epNames[]` to see everything saved on the device (a superset of the active endpoints) before activating or deleting one.
- **Audit routing & security** — review each endpoint's `eventConfiguration` and `securityParams`.

## Topic Mapping

| Message | Direction | Topic | Note |
| --- | --- | --- | --- |
| Request | App → Reader | `<tenantId>/MGMT/clients/cmnd/<serial>` | On the management endpoint. |
| Response | Reader → App | `<tenantId>/MGMT/clients/resp/<serial>` | Correlated reply to the request above; the in-payload `requestId` links the twin topics. |

Topics follow the pattern `<tenantId>/<topic>/<serial>` — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example `RFD40-212735201D0053`). `App → Reader` means your app publishes and the reader subscribes; `Reader → App` means the reader publishes and your app subscribes.

The `publishTopics` / `subscribeTopics` inside the response are **base** topics (e.g. `MDM/clients/cmnd`); on-wire they are wrapped to `<tenantId>/<topic>/<serial>`.

Credentials are presented once at CONNECT. The `requestId` you send is echoed in the response so you can pair reply to request. The endpoint's `mqttParams` govern QoS and retain, not this command.

See [Topics and Channels](/api-reference/mqtt/protocol-reference/topic-structure).

## Key Fields

- **`endpointDetails.endpointName`** (request) — omit for all endpoints; supply to target one (case-sensitive).
- **`activeEndpoints.epConfig[]`** (response) — the full config of each **active** endpoint. Inactive (saved-but-not-activated) endpoints do **not** appear here. An endpoint appears here as soon as it is stored as active, which does not show that it connected: wait for a `CONNECTED` [`mqttConnEVT`](/api-reference/mqtt/events/mqtt-connection-event) on the endpoint’s connection-state topic. See [Saving an endpoint does not connect it](/api-reference/mqtt/mgmt/config-endpoint#overview).
- **`savedEndpoints.epNames[]`** (response) — the names of **all** saved endpoints (active *and* inactive) — the active/saved distinction in one field.
- **`configuration.mqttParams.password`** (response) — ⚠️ a broker credential is present in the response; see [Response Payload](#response-payload) and the credential warning below.
- **`response.code`** (response) — read this to determine success vs failure (see [Response Codes](#response-codes)).

The **7 supported** booleans are exactly the ones you can rely on today; configure event routing with [`config_events`](/api-reference/mqtt/mgmt/config-events).

- **Active vs saved.** `activeEndpoints.epConfig[]` contains a full configuration only for endpoints with `activate: true`. `savedEndpoints.epNames[]` lists **every** saved endpoint — so a name that appears in `epNames` but not in `epConfig[]` is saved but inactive.
- **`verificationType` reads back as you sent it.** The reader returns the value you set with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint), such as `VERIFY_HOST_AND_PEER`; a plain-MQTT endpoint reads back `VERIFY_NONE`. Because one enum governs both directions, you can echo a read-back value in a later `update`.
- **Topic items and the `protocol` literal.** Each `publishTopics` / `subscribeTopics` entry carries `topic`, `qos`, and `retain`. The contract requires `qos` and `retain` on a publish item, and `topic`, `qos` and `retain` on a subscribe item — but its own read-back examples omit `retain` on every subscribe item, and an MQTT subscription has no retain flag, so do not reject a subscribe entry that lacks it. The TLS protocol literal does not differ by direction: you send `MQTT_TLS` with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) and read the same `MQTT_TLS` back here, so a validator can hold one enum — `MQTT` or `MQTT_TLS` — for both directions.
- **Topic slots read back in configured order.** `publishTopics` entries are returned in the order they were set with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint): `[0]` = command responses (`…/clients/resp`), `[1]` = events (`…/clients/event`), `[2]` = the endpoint's connection-event and [Last Will](/api-reference/mqtt/protocol-reference/qos-and-delivery-semantics#retention-and-last-will) topic (`…/clients/rfid`), with `subscribeTopics[0]` = command ingress (`…/clients/cmnd`). A `DATA1` endpoint configured with a placeholder at `[0]` reads the tag-data topic back at `[1]`, as the contract's `DATA1` read-back shows. A read-back with a single entry is read from index `0` upward, so that entry sits in the **reply** slot and no tag data is flowing. Match entries by **index, not base name** — the `resp` / `event` / `rfid` names are conventions.

## Response Codes

`get_endpoint_config` returns `response.code`. The codes applicable to this command are below; for the full table see the [Response Codes](/api-reference/mqtt/response-codes) and [Correlation and Request/Response Pairing](/api-reference/mqtt/protocol-reference/message-envelope#correlation-and-request-response-pairing).

| Code | Description |
| --- | --- |
| `0` | Success — the endpoint configuration was retrieved. |
| `3` | Not able to retrieve information (`IOT_ERROR_INFO_NOT_AVAILABLE`) — the device could not gather the configuration at this time. Retry after a short delay; if persistent, reboot. |
| `101` | Default error — generic catch-all. |

## Examples

Publish `get_endpoint_config`; the device replies with the envelope shown under [Response Payload](#response-payload). The all-endpoints request (`command` + `requestId`) returns every active endpoint plus the saved-names list; the single-endpoint request (shown under [Request Payload](#request-payload)) targets one endpoint by name.

**Active vs saved.** In the response example, `activeEndpoints.epConfig[]` carries the full config of the two active endpoints (`mdm_ep2` and `data1_ep`), while `savedEndpoints.epNames` lists all five saved (`mdm_ep`, `mdm_ep2`, `ctrl_ep`, `data1_ep`, `mgmt_ep`) — the three that are saved but not active appear **only** as names, with no config block. When more than one endpoint is active, `epConfig[]` holds one full configuration per active endpoint.

## Notes and Caveats {#notes--caveats}

:::caution[The response returns broker credentials]
`configuration.mqttParams.password` (and `username`, when set) are part of the read-back. Redact them in logs, tickets, and screenshots; transport and store the response only over secured channels. The examples on this page carry placeholders, not real credentials.
:::
