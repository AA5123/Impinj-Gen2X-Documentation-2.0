> 📕 **REFERENCE** · **Audience:** API Consumer · **Use:** look up what a fixed reader REST response carries and which status codes the specification actually declares

Everything on this page is read out of the vendor's OpenAPI 3.1 document (*IoT Connector REST API (FXR60 / FXR90)*, version 3.0.0) — the same document the [operation reference](/api-reference/rest/endpoints) is generated from. **Nothing here is inferred from HTTP convention.** Where the document is silent, this page says so rather than filling the gap.

:::important[Fixed readers only]
These codes belong to the FXR60 / FXR90 REST surface. The RFD40 / RFD90 handheld sleds speak MQTT, and their application-level codes are a different, much larger set — see [Response Codes](/api-reference/mqtt/response-codes) in the MQTT reference.
:::

### The Declared Status Codes {#declared-status-codes}

Across all 73 operations the document declares **four** distinct HTTP status codes, and no others.

| Status | Declared by | Description in the document | Body |
|---|---|---|---|
| `200` | all 73 operations | `OK` (72) · `Success` (1, the login call) | Varies — see [What a `200` Carries](#what-a-200-carries) |
| `400` | 1 operation | `Error` | `code` + `message` |
| `422` | 1 operation | `Unprocessable Entity` | `message` only |
| `500` | 3 operations | `Error` (1) · `Internal Server Error` (2) | `code` + `message` |

Two things follow from that table and are worth stating plainly:

- **`200` is the entire documented success surface.** No operation declares `201`, `202`, `204` or any other 2xx.
- **There is no catch-all.** The document declares no `default` response, no ranged responses (`4XX`, `5XX`), and no reusable `components.responses` block. A status code not listed above is not defined-and-omitted — it is simply outside the document.

Every declared body, success or error, is `application/json`. No operation declares any other media type.

### What a `200` Carries {#what-a-200-carries}

A `200` does not imply a payload. The 73 success responses fall into four shapes:

| Shape | Operations | What you get |
|---|---|---|
| JSON object | 33 | A populated object — for example the reader identity from [`GET /cloud/version`](/api-reference/rest/endpoints#tag/system/GET/cloud/version) |
| Empty string | 30 | Schema is `type: string`, described as *"Returns an empty string on success."* The shape used by operations that only apply or clear a setting, such as [`PUT /cloud/app-led`](/api-reference/rest/endpoints#tag/app-led/PUT/cloud/app-led) |
| JSON array | 4 | A list |
| No body declared | 6 | The `200` carries a description and no `content` at all: [`PUT /cloud/start`](/api-reference/rest/endpoints#tag/control/PUT/cloud/start), [`PUT /cloud/stop`](/api-reference/rest/endpoints#tag/control/PUT/cloud/stop), [`PUT /cloud/certificates`](/api-reference/rest/endpoints#tag/certificate/PUT/cloud/certificates), [`PUT /cloud/bleConfig`](/api-reference/rest/endpoints#tag/ble/PUT/cloud/bleConfig), [`DELETE /cloud/logs/syslog`](/api-reference/rest/endpoints#tag/logs/DELETE/cloud/logs/syslog) and [`DELETE /cloud/logs/radioPacketLog`](/api-reference/rest/endpoints#tag/logs/DELETE/cloud/logs/radioPacketLog) |

#### The One Application-Level Code in a Success Body {#application-level-code}

Exactly one operation returns a status field *inside* a `200`. [`GET /cloud/localRestLogin`](/api-reference/rest/endpoints#tag/login/GET/cloud/localRestLogin) answers with a two-field object, and the document's own example shows `code` as `0` on success with the bearer token in `message`:

```json
{
  "code": 0,
  "message": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

No other operation's success body carries a `code` field, so **there is no site-wide application-level code scheme on this API.** Read the HTTP status, not a body field — the login call is the single exception. This is the sharpest difference from the handheld MQTT surface, where every reply carries a `response.code`.

### The Three Operations That Declare an Error {#operations-with-errors}

Error responses exist for three operations out of 73. They are listed here in full because the list is the whole documented error surface.

| Operation | Codes | Body of each |
|---|---|---|
| [`PUT /cloud/cableLossCompensation`](/api-reference/rest/endpoints#tag/system/PUT/cloud/cableLossCompensation) | `400`, `500` | `code` + `message` |
| [`GET /cloud/impinjGen2X`](/api-reference/rest/endpoints#tag/impinjgen2x/GET/cloud/impinjGen2X) | `500` | `code` + `message` |
| [`PUT /cloud/impinjGen2X`](/api-reference/rest/endpoints#tag/impinjgen2x/PUT/cloud/impinjGen2X) | `422`, `500` | `422` → `message` only · `500` → `code` + `message` |

**For the other 70 operations the document declares no error response at all.** That is a gap in the document, not a guarantee that those operations never fail.

### The Two Error Body Shapes {#error-body-shapes}

Four of the five error responses use the same object, and the `422` uses a reduced form of it.

**`code` + `message`** — used by every `400` and every `500`:

```json
{
  "code": 0,
  "message": "string"
}
```

`code` is typed `number` and `message` is typed `string`. Neither is marked required, and the document supplies no example for any error body, so the values above are placeholders showing the types, not a real response.

**`message` alone** — used by the single `422`, on [`PUT /cloud/impinjGen2X`](/api-reference/rest/endpoints#tag/impinjgen2x/PUT/cloud/impinjGen2X):

```json
{
  "message": "string"
}
```

Each of the five error responses points at its own schema (`SetCablelosscompensationResponse400`, `SetCablelosscompensationResponse500`, `GetImpinjGen2XResponse500`, `SetImpinjGen2XResponse422`, `SetImpinjGen2XResponse500`) rather than at one shared error model. The shapes coincide; the document does not oblige them to.
