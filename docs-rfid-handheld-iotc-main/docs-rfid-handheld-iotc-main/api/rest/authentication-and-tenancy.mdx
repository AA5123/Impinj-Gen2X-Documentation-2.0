> 📕 **REFERENCE** · **Audience:** API Consumer · **Use:** look up how a call to a fixed reader is authenticated

The FXR60 / FXR90 REST API declares exactly two security schemes, both of them plain HTTP authentication. There is no document-wide default: **every operation names its own scheme**, and the split is one operation against seventy-two.

### The Two Schemes

| Scheme | Type | Used by |
|---|---|---|
| `basicAuth` | HTTP Basic | [`GET /cloud/localRestLogin`](/api-reference/rest/endpoints#tag/login/GET/cloud/localRestLogin) only — 1 operation |
| `bearerAuth` | HTTP Bearer | Every other operation in the document — 72 operations |

Neither scheme carries scopes, and there is no OAuth flow, API-key parameter or signed-request scheme anywhere in the document.

### Obtaining a Token

A bearer token comes from one of two places.

**From the login operation.** [`GET /cloud/localRestLogin`](/api-reference/rest/endpoints#tag/login/GET/cloud/localRestLogin) authenticates with the reader's Admin login credentials over HTTP Basic and returns a token. It takes no request body.

```bash
curl -u '<admin-user>:<admin-password>' \
  '<reader-base-url>/cloud/localRestLogin'
```

The response is a two-field object: `code` is `0` on success, and `message` is the token itself.

```json
{
  "code": 0,
  "message": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**From the reader's dashboard page.** A token copied from the dashboard can be used directly; the login operation exists to mint one when you do not already have it.

### Carrying the Token

Every bearer-secured operation expects the token in a standard `Authorization` header:

```bash
curl -H 'Authorization: Bearer <token>' \
  '<reader-base-url>/cloud/version'
```

The header is the only place the token is read from. No operation in the document accepts it as a query parameter or a cookie.

### The Two Local Accounts

The document names two local accounts, `admin` and `rfidadm`. [`PUT /cloud/updatePassword`](/api-reference/rest/endpoints#tag/system/PUT/cloud/updatePassword) changes the password of one of them:

```json
{
  "userName": "admin",
  "currentPassword": "oldPassword@123",
  "newPassword": "newPassword@123"
}
```

`userName` selects **which** account to update — it does not rename an account and it cannot create one. All three fields are required, and the request fails if `currentPassword` is wrong.

Note the ordering this implies: the password-change operation is itself secured with `bearerAuth`, so you need a valid token before you can rotate the credential the token was minted from. Change the password, then log in again to obtain a token under the new one.
