A reader reports its health in three places: the reply to [`get_status`](/api-reference/mqtt/mgmt/get-status) when you ask, the [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) it publishes at an interval, and the [`alerts`](/api-reference/mqtt/events/alerts-event) it publishes when the battery or power source changes. This page shows how to use each one.

## Check Health on Demand {#on-demand}

1. Subscribe to the endpoint's response topic, for example `<tenantId>/MGMT/clients/resp/<serial>`.
2. Publish `get_status` to the command topic, `<tenantId>/MGMT/clients/cmnd/<serial>`:

   ```json title="get_status — request (illustrative; the contract has no example)"
   {
     "command": "get_status",
     "requestId": "abcd123"
   }
   ```

3. Match the reply by `requestId`. A successful reply has `response.code` `0`, or no `code` and a `description` of `"Success"`.

```json title="get_status — response (contract example: Device status info)"
{
  "command": "get_status",
  "requestId": "abcd123",
  "apiVersion": "V1.21",
  "deviceStatus": {
    "powerSource": "USB",
    "radioActivity": "INACTIVE",
    "radioConnection": "DISCONNECTED",
    "systemTime": "2026-06-15T09:26:00.443Z",
    "ntp": {
      "offset": 0,
      "reach": 0
    },
    "terminalConnection": {
      "status": "CONNECTED",
      "type": "USB"
    },
    "batteryStatus": {
      "mfgDate": "22DEC2024",
      "cycleCount": 8,
      "fullChargeCapacity": 5739,
      "temperature": 24,
      "designCapacity": 6400,
      "batteryType": "LI-ION",
      "capacity": 2467,
      "stateOfHealth": "GOOD",
      "chargePercentage": 46,
      "chargeStatus": 1
    }
  },
  "response": {
    "code": 0,
    "description": "Success"
  }
}
```

`deviceStatus` always carries `powerSource`, `radioActivity` (whether the radio is transmitting), `radioConnection` (whether the RFID radio module is attached and reachable) and `systemTime`. It can also carry the device `temperature` in degrees Celsius, `terminalConnection`, `ntp` and `batteryStatus`. The firmware version comes from [`get_version`](/api-reference/mqtt/mgmt/get-version), not from `get_status`.

## Follow the Battery Continuously {#battery-health}

- **The heartbeat** carries `data.batteryAlert` when the heartbeat is enabled with `heartbeatConfiguration.batteryStatus` set to `true`. It arrives at the configured interval on the event topic, for example `<tenantId>/MGMT/clients/event/<serial>`; see [Configure Event Reporting](/guides/operate-and-monitor/configure-event-reporting).
- **A `BATTERY` alert** carries `alertDetails.batteryAlert` when the `battery` event flag is enabled. See [Respond to Alerts](/guides/operate-and-monitor/respond-to-alerts).

Both use the same `batteryAlert` block. This alert is one of the contract's published examples:

```json title="alerts — event (contract example: Battery alert)"
{
  "type": "ALERT",
  "timestamp": "2026-04-29T12:33:34.279Z",
  "state": "ONESHOT",
  "id": "BATTERY",
  "priority": "LOW",
  "alertDetails": {
    "batteryAlert": {
      "status": "CHARGING",
      "stateOfHealth": "GOOD",
      "chargePercentage": 100
    }
  }
}
```

## Interpret the Battery Fields {#interpret-stateofhealth}

| Field | Where | Values | Meaning |
|---|---|---|---|
| `stateOfHealth` | `get_status`, heartbeat, `BATTERY` alert | `GOOD`, `CRITICAL`, `MODERATE` | Long-term capacity and performance of the battery |
| `status` | Heartbeat, `BATTERY` alert | `LOW`, `CRITICAL`, `CHARGING`, `FULL`, `HIGH` | Charge state |
| `chargePercentage` | All three | 0 to 100 | Charge remaining |
| `chargeStatus` | `get_status` | `0`, `1`, `2` | `0`: charger not connected. `1`: charger connected and charging. `2`: charger connected and battery at 100%. |
| `capacity`, `fullChargeCapacity`, `designCapacity` | `get_status` | mAh | Charge remaining; what the pack holds today; its nameplate rating |
| `cycleCount` | `get_status` | Count | Completed charge cycles |
| `temperature` (in `batteryStatus`) | `get_status` | Degrees Celsius | Battery temperature |

`stateOfHealth` uses one vocabulary everywhere, so the same code can read it from any of the three surfaces. Keep it separate from `status`, which is the charge state rather than a health grade. The charge percentages at which `status` changes are not specified in the available sources.

## Measure Drain in Your Deployment {#drain-characterisation}

Drain depends on the operating mode, the tag population and how long inventories run, and the available sources give no per-mode figures. Record `chargePercentage` from the heartbeat over a representative shift to measure it. A longer heartbeat interval, and stopping inventory between scans, both reduce the traffic the reader generates.
