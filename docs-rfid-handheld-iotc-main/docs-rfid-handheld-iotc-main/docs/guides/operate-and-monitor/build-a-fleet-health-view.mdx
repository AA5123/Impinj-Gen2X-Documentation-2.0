A fleet view combines the events that every reader publishes into one record per reader. This page shows how to collect those events, attribute them to readers, and derive the indicators a dashboard shows.

**Before you start:** each reader has its heartbeat and alerts enabled ([Configure Event Reporting](/guides/operate-and-monitor/configure-event-reporting)), and your application can subscribe to the tenant's topics on the broker.

## 1. Subscribe Across the Fleet {#subscribe}

Every topic ends with the reader's serial number, which the reader appends itself. Put an MQTT single-level wildcard (`+`) in that position to receive a topic from every reader in the tenant:

| Subscription | Receives |
|---|---|
| `<tenantId>/MGMT/clients/event/+` | `heartBeatEVT` and `alerts` from every reader |
| `<tenantId>/MGMT/clients/rfid/+` | `mqttConnEVT` from every reader's management endpoint |

These topic names follow the conventional endpoint configuration. If your endpoints use different topic segments, subscribe to those instead; see [Topics and Channels](/api-reference/mqtt/protocol-reference/topic-structure). If a reader routes tag data to its management endpoint, `dataEVT` also arrives on the `rfid` topic.

## 2. Attribute Each Message to a Reader {#attribute}

Take the serial number from the last segment of the topic. Then identify the message by its fields, because events carry no field that names their kind:

| Message | Identified by |
|---|---|
| `heartBeatEVT` | `eventName` is `"heartbeat"` |
| `alerts` | `type`, `timestamp`, `state`, `id` and `priority` are present |
| `mqttConnEVT` | `connectionState` is present |
| `dataEVT` | `type` and `data` are present |

The following sketch shows the pattern. It is illustrative and has not been run against a reader:

```python
fleet = {}  # serial number -> latest state

def on_message(topic, payload, received_at):
    serial = topic.rsplit("/", 1)[-1]
    reader = fleet.setdefault(serial, {"alerts": []})
    if payload.get("eventName") == "heartbeat":
        reader["last_heartbeat"] = received_at
        reader.update(payload.get("data", {}))  # inventoryStatus, batteryAlert
    elif "connectionState" in payload:
        reader["connection"] = payload["connectionState"]
        reader["connection_changed"] = received_at
    elif {"type", "state", "id", "priority"} <= payload.keys():
        reader["alerts"].append(payload)
```

Record the time your application received each message as well as any `timestamp` the message carries. The Last Will form of `mqttConnEVT` has no timestamp, because the broker publishes it on the reader's behalf.

## 3. Derive the Indicators {#indicators}

| Indicator | Derived from |
|---|---|
| Readers online | Readers whose last `heartBeatEVT` arrived within the number of intervals you treat as an outage |
| Session changes | `mqttConnEVT` transitions per reader over time |
| Battery | `batteryAlert.chargePercentage`, `status` and `stateOfHealth` from heartbeats and `BATTERY` alerts |
| Inventories running | `inventoryStatus.rfidStatus` of `INPROGRESS` in heartbeats that carry the block |
| Alerts | Counts by `id` and `priority` over a time window |

The heartbeat is published at QoS 0 and a lost one is not resent, so count an outage in missed intervals rather than from a single gap.

**Result:** one record per reader, updated as events arrive, from which a dashboard can draw the fleet's state.
