Once a reader is in service, your application learns about it from four sources:

| Source | What it tells you | How it arrives |
|---|---|---|
| `heartBeatEVT`, the periodic heartbeat | That the reader is still publishing, with battery and inventory status | At the configured interval, at QoS 0 |
| `mqttConnEVT` and the Last Will | That a session started, or ended without a clean disconnect | On the endpoint's connection-state topic, at QoS 0 |
| `alerts` | That a condition changed: battery, power, network, firmware update or file download | On the event topic, at QoS 1 |
| `get_status` | The reader's power, battery, radio and clock state, when you ask | As a reply to your command |

`heartBeatEVT` and the `alerts` conditions are enabled with `config_events`, and a change takes effect after a reboot. None of these events is reliably retained, so subscribe before you rely on them. Start with [What to Monitor and Why](/guides/operate-and-monitor/what-to-monitor-and-why), then [Configure Event Reporting](/guides/operate-and-monitor/configure-event-reporting).
