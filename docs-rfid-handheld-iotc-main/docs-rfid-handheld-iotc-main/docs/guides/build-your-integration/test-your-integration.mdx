The MQTT API is defined by a contract file written in AsyncAPI 3.0.0, the standard format for describing event-driven APIs, and its payload schemas are a superset of JSON Schema Draft 07. The reader itself speaks MQTT 3.1.1. That makes much of an integration testable without a reader: you can validate what your application sends, feed it the messages a reader publishes, and break things on purpose. This page shows how.

## Step 1: Validate What You Send {#validate-commands}

Validate every command your application builds against the contract before it reaches a broker:

1. Get the schemas. Each command's page in the [MQTT API](/api-reference/mqtt) reference shows its schema; this site does not publish the contract file itself for download.
2. Validate each command against its schema with a JSON Schema Draft 07 validator. The contract does not close its messages, so a misspelled property passes validation; check property names against the operation pages as well.
3. Run the validation in your automated tests, so that a change to the payload code cannot silently break a command.

Remember the property names that surprise people: `OSUpdateDetails` on `set_os`, `ctrlOprPayload` on `control_operation`, and the two levels `operatingMode.operatingModes` on `set_operating_mode`.

## Step 2: Parse What the Reader Sends {#replay}

Feed your parsing code the reply and event examples each reference page reproduces. Also test the success reply without a code described in [Success Without a Code](/api-reference/mqtt/protocol-reference/message-envelope#success-omits-code). Include the forms that trip parsers:

- A reply with no `code`, only `"description": "Success"`.
- `mqttConnEVT` with `apiVersion` and `mqttVersion` as numbers, such as `3.0999999`, and the Last Will form with no `timestamp`.
- `dataEVT` records with only some fields, and hex values in either case.
- `alerts` whose `fwUpdateStatus.updateStatus` is a display sentence rather than a fixed value.

Treat a message your code cannot classify as a finding: log it instead of dropping it silently.

## Step 3: Simulate Events on a Test Broker {#simulate}

Run a broker you control, and publish recorded or example messages to the reader's topics with a command-line client:

```bash
mosquitto_pub -h localhost -t 'acme/MGMT/clients/event/RFD40-211545201D0034' \
  -m '{"type":"ALERT","timestamp":"2026-04-29T12:33:34.279Z","state":"ONESHOT","id":"BATTERY","priority":"LOW","alertDetails":{"batteryAlert":{"status":"CHARGING","stateOfHealth":"GOOD","chargePercentage":100}}}'
```

The payload is the contract's "Battery alert" example. A simulator publishes what your application expects to receive; it cannot show how a real reader behaves, so test against a reader before production.

## Step 4: Test the Failure Paths {#failure-paths}

| Break | What your application should do |
|---|---|
| Drop replies (do not answer a command) | Time out, read the state back, and not resend blindly |
| Deliver a reply twice | Ignore the second copy |
| Deliver an alert twice | Handle it once |
| Stop the application during an inventory, then restart it | Resubscribe, re-read state, and mark the gap as missing evidence |
| Restart the broker | Reconnect, resubscribe and re-read state |
| Stop the heartbeats from one reader | Raise the outage your policy defines |
| Send a code `11` or `4` reply | Clear the condition or wait, and not retry in a tight loop |
| Send a message larger than you expect, or a `dataEVT` with unknown fields | Parse what it recognizes, and not crash |

## Step 5: Test Against a Reader {#reader}

Before production, repeat the key paths with a real reader: a full inventory, a firmware update followed through its alerts, a restart, and a Wi-Fi outage. Several behaviors are not settled in the contract, such as whether `mqttConnEVT` is retained and how stop conditions combine, and only a reader on your firmware can show them.
