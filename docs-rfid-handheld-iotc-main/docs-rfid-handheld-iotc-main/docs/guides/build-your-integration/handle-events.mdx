The reader publishes four kinds of event on its own: [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event), [`alerts`](/api-reference/mqtt/events/alerts-event), [`mqttConnEVT`](/api-reference/mqtt/events/mqtt-connection-event) and [`dataEVT`](/api-reference/mqtt/data/tag-data-event). None of them carries a `requestId` or a `response`, and no field names which kind a message is. This page shows how to tell them apart and handle each one.

## Recognize Each Event by Its Shape {#recognize}

Route by topic first, then by the fields a message carries:

| Event | Arrives on | Recognize it by |
|---|---|---|
| `heartBeatEVT`, the periodic heartbeat | The event topic | `eventName` equal to `"heartbeat"` |
| `alerts` | The event topic | `type`, `timestamp`, `state`, `id` and `priority`, with `id` one of `BATTERY`, `FILE_DOWNLOAD`, `FIRMWARE_UPDATE`, `NETWORK_EVENT`, `POWER` |
| `mqttConnEVT` and the Last Will | The connection-state topic | `connectionState` |
| `dataEVT` | A data endpoint's tag-data topic, or a shared endpoint's connection-state topic | `type`, `timestamp` and `data` |

`alerts` and `dataEVT` both carry `type` and `timestamp`, and their `type` values come from different vocabularies: `EVENT`, `NOTIFICATION` or `ALERT` for an alert, and an operating-mode profile such as `BALANCED_PERFORMANCE` for tag data. When tag data shares a topic with `mqttConnEVT`, check for `connectionState` and `data` rather than relying on the topic.

```python
def classify(message: dict) -> str:
    if message.get("eventName") == "heartbeat":
        return "heartBeatEVT"
    if "connectionState" in message:
        return "mqttConnEVT"
    if "data" in message:
        return "dataEVT"
    if {"id", "state", "priority"} <= message.keys():
        return "alerts"
    return "unknown"      # log it; do not guess
```

## Handle Each Event {#handle}

- **`heartBeatEVT`.** Record its arrival time per reader. When heartbeats stop arriving, the reader, its session, or the path to your application needs attention; how many missed intervals count as an outage is your choice. Its `data` block carries only what is enabled, so treat every member as optional. See [Monitor Reader Connectivity](/guides/operate-and-monitor/monitor-reader-connectivity).
- **`alerts`.** Branch on `id`, read the matching member of `alertDetails`, and use `priority` (`CRITICAL`, `HIGH` or `LOW`) to decide urgency. `state` is `SET`, `CLEAR` or `ONESHOT`; the contract states no rule for which alerts latch, so do not wait for a `CLEAR` that may never come. See [Respond to Alerts](/guides/operate-and-monitor/respond-to-alerts).
- **`mqttConnEVT`.** Record `CONNECTED` and `DISCONNECTED` with their arrival times. The `DISCONNECTED` form published by the broker as the Last Will carries no `timestamp`, so use your own receive time. After `CONNECTED`, refresh your view of the reader; see [Recover from Disconnects](/guides/build-your-integration/recover-from-disconnects#after-reader-reconnect).
- **`dataEVT`.** See [Consume Tag Data](/guides/build-your-integration/consume-tag-data).

## Absorb Duplicates {#duplicates}

`alerts` travel at QoS 1, which delivers a message at least once, so the same alert can arrive twice. Make your handling idempotent: key an alert on its `id`, `state` and `timestamp`, and ignore a repeat you have already handled.

## Allow for the Retain Flag on `mqttConnEVT` {#retain}

The contract does not settle whether `mqttConnEVT` is retained: one declaration says it is, another says it is not. If it is retained, a new subscriber immediately receives the last connection state, which may be old. Do not treat a `mqttConnEVT` received right after you subscribe as a new transition; compare its `timestamp`, when present, with the time you subscribed.

## Keep Events and Replies Apart {#events-and-replies}

A command reply carries `command`, `requestId` and `response`; an event carries none of them. If a message on a response topic has no `requestId`, it is not a reply to your command.
