A reader in a dense tag population produces reads faster than an acknowledged flow can confirm them, which is why the reader's default endpoint configurations send tag data at QoS 0. You set the QoS of the tag-data topic, 0 or 1, when you configure the data endpoint. This page shows the levers that control how much tag data reaches your broker and your applications. The contract states no tag rates, so measure your own.

## Know the Limits {#limits}

- **6144 bytes per message.** A whole `dataEVT` message is limited to 6144 bytes. A larger one is dropped by the reader, with no error, and the connection stays up.
- **No limit on records.** There is no maximum number of tag records in a message; the endpoint's batching settings bound it.
- **Batching per endpoint.** Each endpoint's `batching` block decides when a batch is published.

## Lever 1: Tune Batching {#batching}

Each endpoint's `batching` block has two members. A batch is published when either limit is reached:

| Member | Default data endpoint | Declared range |
|---|---|---|
| `reportingInterval` | `1000` ms | `1000` to `60000` ms |
| `maxPayloadSizePerReport` | `1024` bytes | `1024` to `5120` bytes |

A longer interval and a larger size mean fewer, larger messages. Sending `0` for a member does not turn batching off: the reader uses that member's minimum. Send both members together; the contract does not say what happens when you set only one. See [How Reads Become Messages](/guides/core-concepts/the-tag-data-stream#batching).

## Lever 2: Trim the Fields {#fields}

Every field a tag record carries adds bytes. Switch off the metadata flags you do not use, especially `TID`, `USER`, `MAC` and `HOSTNAME`. See [Choose Which Tag Fields Are Reported](/guides/read-tags-and-barcodes/choose-tag-data-fields).

## Lever 3: Filter Before Publishing {#filter}

- **Pre-filters** narrow the tag population the radio inventories at all. See [Pre-Filter Tags with Select](/guides/read-tags-and-barcodes/pre-filter-tags-with-select).
- **Post-filters** decide which read tags each data endpoint reports. See [Post-Filter Reported Tags](/guides/read-tags-and-barcodes/post-filter-reported-tags).

## Lever 4: Use Dedicated Endpoints {#endpoints}

Put tag data on a dedicated `DATA1` endpoint rather than a shared management endpoint, so that it does not share a topic with connection-state messages. A dedicated endpoint can point at a different broker. (`DATA2` is currently not supported.) See [Choose Shared or Dedicated Data Endpoints](/guides/build-your-integration/choose-shared-or-dedicated-data-endpoints).

## Lever 5: Size the Broker and the Consumers {#sizing}

- **Estimate the load** from your own measurements: messages per second per reader, times the average message size, times the number of readers.
- **Keep consumers fast.** Parse and hand off; do slow work, such as database writes, elsewhere. A consumer that falls behind loses QoS 0 messages.
- **Consider QoS per topic.** Each data endpoint's tag-data topic has its own `qos`: 0 or 1, the two levels the reader supports. QoS 1 adds acknowledgements and duplicates; QoS 0 accepts loss. Whatever you choose, the contract describes the stream as a statistical view, not a guaranteed log.

## Check the Result {#check}

After a change, run an inventory in the real environment and compare what you receive with what you expect. Missing messages after you add fields or enlarge batches point at the 6144-byte limit. See [Test and Validate Performance](/guides/read-tags-and-barcodes/improve-read-performance#test-and-validate-performance).
