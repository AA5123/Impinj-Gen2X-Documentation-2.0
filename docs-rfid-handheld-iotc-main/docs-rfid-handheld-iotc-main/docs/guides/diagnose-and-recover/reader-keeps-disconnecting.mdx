**Applies when:** `mqttConnEVT` alternates between `CONNECTED` and `DISCONNECTED`, or the broker's log shows the reader connecting again and again.

Work through the checks in order, and stop at the first one that fails.

1. **Does the keep-alive suit the network?** `mqttParams.keepAlive` is in seconds; the contract's binding uses 300. In MQTT 3.1.1 the broker drops a client it has not heard from for one and a half times the interval, and a firewall that drops idle connections sooner breaks the session too.
2. **Is another client using the same client ID?** In MQTT 3.1.1 the broker disconnects the older of two clients with the same client ID, so two readers, or a reader and a test client, sharing one keep displacing each other. See [FM-NET-03](/guides/diagnose-and-recover/diagnose-by-system-area#fm-net-03).
3. **Are the reconnect delays sensible?** `reconnectDelayMin` and `reconnectDelayMax` bound how long the reader waits before reconnecting. The contract does not describe the back-off between them.
4. **Is the network changing under the reader?** Enable the `network` flag and watch `alerts` with `id: "NETWORK_EVENT"`, and compare [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi) over time for changes of network or address.
5. **Does the Last Will arrive?** The broker publishes it, a `DISCONNECTED` event without a timestamp, only when the session ends without a clean disconnect. Frequent Wills point at lost connections — power, Wi-Fi or the network path — rather than at the reader closing its session.

**If none apply:** collect the evidence in [Escalate to Support](/guides/diagnose-and-recover/escalate-to-support).
