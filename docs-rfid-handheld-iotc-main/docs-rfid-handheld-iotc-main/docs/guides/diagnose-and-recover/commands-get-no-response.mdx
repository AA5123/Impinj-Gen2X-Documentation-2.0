**Applies when:** you publish a command and no reply arrives on the response topic you are watching.

Work through the checks in order, and stop at the first one that fails.

1. **Did you subscribe before you published?** Replies are not retained; a reply published before your subscription was active is lost. Subscribe, then send the command again with a new `requestId`. See [Subscribe Before You Publish](/guides/core-concepts/delivery-retries-and-disconnects#subscribe-first).
2. **Does the topic contain the tenant ID or serial number twice?** The reader adds both to every configured topic, so a `topic` that already contains them produces a topic nothing uses. See [How a Topic Is Built](/guides/core-concepts/endpoints-topics-and-channels#topic-format).
3. **Does your topic use the serial form the reader uses?** Use the model-prefixed form directed by the contract: `model`, a hyphen and `serialNumber`. Subscribe with `+` in the serial position to inspect messages across readers. See [RP-03](/guides/diagnose-and-recover/recovery-playbooks/restore-mqtt-connectivity#rp-03).
4. **Is the command topic the endpoint's subscribe topic, and is `publishTopics[0]` set?** The reader receives commands only on its single subscribe topic and publishes replies on its first publish topic. Read both with [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) over another endpoint. See [Publish Topics Are Slots](/guides/core-concepts/endpoints-topics-and-channels#publish-topic-slots).
5. **Is the endpoint active and connected?** Look for a `CONNECTED` `mqttConnEVT` on its connection-state topic. If there is none, see [Cannot Connect to the Broker](/guides/diagnose-and-recover/cannot-connect-to-the-broker).
6. **Is your subscription at QoS 1?** In MQTT 3.1.1, a subscription at QoS 0 downgrades delivery of QoS 1 replies, and a reply can then be lost.
7. **Was it an asynchronous command?** `set_os`, `install_certificate` and `reboot` reply with code `1` and finish later; `reboot` then drops the session. The contract specifies no timeout for any command. See [Track Asynchronous Commands](/guides/build-your-integration/track-asynchronous-commands).
8. **Is a firmware update running, or have you sent many commands at once?** During an update every command is refused with code `4`. The reader queues at most 10 commands, and commands beyond that are lost.

**If none apply:** collect the evidence in [Escalate to Support](/guides/diagnose-and-recover/escalate-to-support).
