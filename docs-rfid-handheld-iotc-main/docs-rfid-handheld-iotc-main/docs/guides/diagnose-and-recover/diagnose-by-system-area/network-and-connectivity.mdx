**Scope.** The path from the reader to the broker: Wi-Fi association, DHCP, DNS, firewalls and ports, reconnect behavior, and the reader's Ethernet interface. If the reader has a working path and the fault is inside the MQTT session — TLS, credentials, access rules, topics — see [MQTT Connection](/guides/diagnose-and-recover/diagnose-by-system-area/mqtt-connection).

The commands on this page are read commands, safe to send again. Send them to the reader's management command topic, for example `<tenantId>/MGMT/clients/cmnd/<serial>`, and read the replies on `<tenantId>/MGMT/clients/resp/<serial>`, using the middle segments your endpoint is configured with. If the reader has no MQTT path at all, you cannot send them; use 123RFID Desktop over USB-C instead.

## Before You Start: Place the Fault {#place-the-fault}

1. **Watch the connection-state topic**, the endpoint's third publish topic, conventionally `<tenantId>/MGMT/clients/rfid/<serial>`, for `mqttConnEVT`. The reader publishes `CONNECTED` when a session starts; the broker publishes the Last Will, a `DISCONNECTED` event without a `timestamp`, when a session ends without a clean disconnect.
2. **Send [`get_status`](/api-reference/mqtt/mgmt/get-status).** Any reply proves that the path from your application through the broker to the reader and back works.
3. **Place the fault:**

| What you see | Where the fault is | Go to |
|---|---|---|
| `get_status` replies | The path works; the fault is elsewhere | [MQTT Connection](/guides/diagnose-and-recover/diagnose-by-system-area/mqtt-connection) or [Endpoints and Configuration](/guides/diagnose-and-recover/diagnose-by-system-area/endpoints-and-configuration) |
| No reply and no `CONNECTED` since the last change | The reader cannot reach or join the broker | [Wi-Fi Association Fails](#wifi-association) onward |
| `CONNECTED` and `DISCONNECTED` alternating | A reconnect loop | [The Reader Keeps Reconnecting](#flapping) |

`get_status.deviceStatus.radioConnection` reports the RFID radio module, not the network, so it says nothing about Wi-Fi.

## Wi-Fi Association Fails {#wifi-association}

When the reader is reachable over another endpoint, or after you restore a connection, send [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi) and read the connected profile:

| Field | Healthy | If not |
|---|---|---|
| `interfaceDetails.status` | Enabled | The Wi-Fi interface is disabled, and the reply carries only the interface name and status |
| `accessPoint.status` | `CONNECTED` | The reader has not joined: wrong passphrase, Enterprise credentials or certificates, network out of range, or a `securityType` that does not match the network |
| `accessPoint.essid` | The network you expect | The reader joined another saved profile; mark the right one `isPreferred` |
| `ipv4Configuration.ipAddress` | Present | Joined but unaddressed: see [DHCP Fails](#dhcp) |

The reader reports states in more than one letter case, such as `Enabled` and `ENABLED`; compare without regard to case.

**Fix:** correct the profile with [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi) `MODIFY`, or with 123RFID Desktop if the reader has no other path. For an Enterprise profile, install its certificates first. See [Configure Wi-Fi](/guides/manage-your-reader/configure-wi-fi) and [FM-NET-04](/guides/diagnose-and-recover/diagnose-by-system-area#fm-net-04).

| Code | Meaning | Fix |
|---|---|---|
| `2` | Invalid payload | Correct the payload against the command's schema |
| `15` | SSID not found | Check the ESSID, or use `CREATE` |
| `16` | Cannot delete active SSID | Connect to another profile first |
| `17` | SSID missed | Include `essid` |
| `18` | SSID already exist | Use `MODIFY` |
| `19` | SSID count overflow | Delete an unused profile; the contract does not state the maximum |
| `20` | Wifi is not supported | The reader has no Wi-Fi interface |
| `23` | Invalid enum value | Correct the value |

## DHCP Fails {#dhcp}

`get_wifi` shows the profile `CONNECTED` but `ipv4Configuration.ipAddress` is empty. The reader joined the network but did not get an address. Check that the network's DHCP server has free addresses and does not block the reader's MAC address, `interfaceDetails.macAddress`. The command's source states that static IPv4 configuration is not available in the current API version, so fix DHCP rather than configuring an address.

## DNS Fails {#dns}

The reader has an address but never connects to a broker given by host name. Check `ipv4Configuration.dnsServer` and `gateway` in `get_wifi`, and resolve the broker's host name from a computer on the same network. While you debug, an endpoint that uses the broker's IP address in `url` takes DNS out of the path.

## A Firewall Blocks the Port {#firewall}

The reader has an address, and the broker sees no connection. From a computer on the reader's network:

```bash
nc -vz <broker-host> 8883
```

Use `1883` for a plain MQTT endpoint. Check with [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) that the endpoint is `activate: true`, and that its `url`, `port` and `protocol` agree: `MQTT` with `1883`, `MQTT_TLS` with `8883`. The reader does not cross-check `protocol` and `port`. See [FM-NET-01](/guides/diagnose-and-recover/diagnose-by-system-area#fm-net-01).

## The Reader Keeps Reconnecting {#flapping}

`mqttConnEVT` alternates between `CONNECTED` and `DISCONNECTED`. The usual causes:

1. **A shared client ID.** In MQTT 3.1.1, the broker disconnects the older of two clients with the same client ID. Give each reader and each application its own.
2. **A keep-alive longer than the network's idle timeout.** A firewall that drops idle connections sooner than `mqttParams.keepAlive` breaks the session. The contract's binding uses 300 seconds; match it to your network.
3. **A broker access rule** that rejects the reader's topics after it connects. The broker's log usually names it.
4. **The Wi-Fi link itself**, when the reader moves between access points or has a weak signal. Watch `NETWORK_EVENT` alerts, if enabled, and compare `get_wifi` over time.

`reconnectDelayMin` and `reconnectDelayMax` bound how long the reader waits before reconnecting; the contract does not describe the back-off between them. See [FM-NET-03](/guides/diagnose-and-recover/diagnose-by-system-area#fm-net-03).

An endpoint cannot be changed while it is active (code `35`), so correct an endpoint through the staged procedure in [Configure MQTT Endpoints](/guides/manage-your-reader/configure-mqtt-endpoints#stage-and-activate).

## Ethernet Shows No Link {#ethernet}

[`get_eth`](/api-reference/mqtt/mgmt/get-eth) reports the reader's Ethernet interface. When the interface is disabled, the reply is still code `0` and carries only `interfaceName` and `status`. When it is enabled, check:

| Field | Healthy | If not |
|---|---|---|
| `linkStatus.status` | Connected | No physical link |
| `linkStatus.linkSpeed` | The speed you expect | A cable or switch-port problem |
| `ipv4Configuration.ipAddress` | Present | DHCP failed |

The MQTT API has no command that changes Ethernet settings. Which reader hardware exposes an Ethernet interface is not specified in the available sources.

## Diagnostic Sequence {#sequence}

Run these in order, and stop at the first one that fails:

1. [`get_status`](/api-reference/mqtt/mgmt/get-status): does the reader reply at all?
2. [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi): is it on the right network, with an address?
3. [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config): is the endpoint active, with the right `url`, `port`, `protocol` and `verificationType`?
4. Over a few heartbeat intervals, do `heartBeatEVT` and `mqttConnEVT` show a steady session?

If every step passes and the problem persists, it is not on the path: see [MQTT Connection](/guides/diagnose-and-recover/diagnose-by-system-area/mqtt-connection) and [Application Integration](/guides/diagnose-and-recover/diagnose-by-system-area/application-integration).
