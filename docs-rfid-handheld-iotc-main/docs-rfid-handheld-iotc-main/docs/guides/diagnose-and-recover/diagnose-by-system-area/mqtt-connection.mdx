**Scope.** The MQTT session between reader and broker: CONNECT succeeding or not, TLS, credentials and ACLs, keep-alive, and whether commands and events actually traverse the session.

This area assumes the reader already has an IP address and can route to the broker's host and port. If it cannot, that is [Network and Connectivity](/guides/diagnose-and-recover/diagnose-by-system-area/network-and-connectivity). If the session is up but the *endpoint definitions* are wrong, that is [Endpoints and Configuration](/guides/diagnose-and-recover/diagnose-by-system-area/endpoints-and-configuration).

## Read the Session State First

`mqttConnEVT` on the endpoint's connection-state topic, together with the Last Will the broker publishes for the reader, separates the common shapes of failure. It is evidence, not certainty: a clean disconnect publishes no Will, and a message can be lost at QoS 0.

| What you see | What it means |
|---|---|
| No `mqttConnEVT` has ever arrived | The reader is not completing CONNECT — reachability, credentials or TLS — or you are not subscribed to the connection-state topic |
| One `DISCONNECTED`, then nothing | The session dropped and reconnect is failing |
| Alternating `CONNECTED` / `DISCONNECTED` | A reconnect loop — client-ID collision, ACL rejection, or keep-alive |
| `CONNECTED` and current, but nothing else arrives | The session is fine; the fault is in routing or subscriptions |

## Isolate TLS from Authentication

When both TLS and credentials are unproven, you are chasing two variables at once. On a trusted test network, try a plain `MQTT` endpoint on `1883` first; the reader refuses to change an active endpoint, so add a separate test endpoint rather than downgrading the one in use. If the session comes up, the credentials and ACLs are correct and the fault is in the certificate chain or `verificationType`; put TLS back and work [FM-SEC-01](/guides/diagnose-and-recover/diagnose-by-system-area#fm-sec-01). If it still fails on `1883`, TLS was never the problem.

Match the protocol to the port every time: `MQTT` with `1883`, `MQTT_TLS` with `8883`. The reader does not cross-check them, and a mismatch fails to connect.

## What Is Lost While the Session Is Down

The contract describes no store-and-forward: nothing in it says the reader keeps events or tag data while its session is down and sends them later. Plan as if anything published during an outage is lost, and re-read the reader's state after it reconnects — see [Recover from Disconnects](/guides/build-your-integration/recover-from-disconnects).
