**Scope.** The code you wrote against the MQTT API: correlating replies, reading `response.code`, building payloads the reader accepts, parsing events, and retrying safely.

The signature of this area is that the reader is demonstrably healthy — [`get_status`](/api-reference/mqtt/mgmt/get-status) answers, `mqttConnEVT` is current, heartbeats arrive — and the failure is reproducible from your client and only from your client. If the reader itself is not answering, this is the wrong area; start at [MQTT Connection](/guides/diagnose-and-recover/diagnose-by-system-area/mqtt-connection).

## This Page Routes; Other Pages Do the Work

Almost everything in this area is documented in depth elsewhere:

- **[Send Commands and Handle Responses](/guides/build-your-integration/send-commands-and-handle-responses)** turns a `response.code` into an action.
- **[Retry Commands Safely](/guides/build-your-integration/retry-commands-safely)** covers when a command can be sent again.
- **[Handle Events](/guides/build-your-integration/handle-events)** and **[Consume Tag Data](/guides/build-your-integration/consume-tag-data)** cover parsing what the reader publishes.

## Start With

| Symptom | Go to |
|---|---|
| Replies arrive but you cannot tell which request they answer | `requestId` is the only correlation mechanism — [Send Commands and Handle Responses](/guides/build-your-integration/send-commands-and-handle-responses) |
| A payload copied from another source is rejected | Compare it field by field with the contract example on the command's reference page |
| A valid-looking enum value is rejected with code `23` | Enum case varies by command: `add` for endpoints, `CREATE` for Wi-Fi, `ADD` for post-filters, `START` for control |
| Your `mqttConnEVT` parser fails | `timestamp` is absent on the Last Will, and `apiVersion` and `mqttVersion` are numbers ([Handle Events](/guides/build-your-integration/handle-events)) |
| A command returned code `1` and you treated it as done | Code `1` is acceptance, not completion — wait for the `alerts` outcome ([Send Commands and Handle Responses](/guides/build-your-integration/send-commands-and-handle-responses)) |
| Retrying a write produced a duplicate or a confusing second reply | The reader executes every copy; read the state back before a resend ([Retry Commands Safely](/guides/build-your-integration/retry-commands-safely)) |
| QoS 1 did not guarantee your application saw every message | QoS applies between one client and the broker; a message published before you subscribed is not delivered ([Delivery, Retries, and Disconnects](/guides/core-concepts/delivery-retries-and-disconnects)) |
| Tag data is missing for the time the connection was down | Expected: the contract describes no store-and-forward ([Recover from Disconnects](/guides/build-your-integration/recover-from-disconnects)) |
| Duplicate tag records in your pipeline | Expected; deduplicate in the application ([Consume Tag Data](/guides/build-your-integration/consume-tag-data)) |

## Prove It Is Your Client

Before you debug your code, reproduce the same command from a bare MQTT client — publish the payload by hand and watch the response topic. Two outcomes, and they point in opposite directions:

- **The bare client gets the same failure.** The payload or the topic is wrong. Compare it field-for-field against the [MQTT API](/api-reference/mqtt) reference, not against an example you adapted.
- **The bare client succeeds.** The reader and the payload are fine. The fault is in your correlation, your subscription, your parser, or your retry logic.
