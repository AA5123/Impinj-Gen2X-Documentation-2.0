A named profile sets the radio for you. When no profile meets the requirement, the operating mode exposes the settings underneath it. This page shows how to set each one with [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode). Start with [Choose a Performance Profile](/guides/read-tags-and-barcodes/choose-a-performance-profile) if you have not chosen a profile yet.

Every member of `operatingMode.operatingModes` is optional, and `set_operating_mode` accepts a partial update, so each example below changes one part of the mode. For all of them:

- Stop any running inventory first. The reader refuses `set_operating_mode` with code `11` during an inventory.
- Read the result back with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode).
- Re-apply the mode after a restart. It is lost on reboot.

## Advanced RF Configuration {#advanced-rf-configuration}

With `profiles: "ADVANCED"`, the reader uses the radio settings you give in `advancedConfigurations` instead of choosing them itself. The block is required with `ADVANCED`; without it the reply is code `22`.

| Member | Meaning |
|---|---|
| `transmitPower` | Transmit power, declared from `0` to `300`. Its unit is unresolved; see the caution below |
| `linkProfile` | The air-interface link profile: `M4_256K`, `M2_240K`, `M2_256K`, `M2_320K`, `M4_240K`, `M4_320K`, `FM0_0K`, `FM0_320K`, `M8_240K`, `M8_256K` or `M8_320K`. `FM0` is FM0 baseband, `M2`, `M4` and `M8` are Miller subcarrier encodings, and the suffix is the backscatter link frequency in kHz |
| `session` | The EPC Gen2 session, `SESSION_0` to `SESSION_3`. `query.session` sets the same thing, and the contract does not say which wins if you send both |
| `dynamicPower` | `true` lets the radio adjust transmit power during an inventory. Whether `transmitPower` then acts as a ceiling or a starting point is not documented |

The contract describes faster link profiles as reading more tags per second, and higher Miller orders as more robust with many readers and multipath.

:::caution[Confirm the applied transmit power]
`transmitPower` has a range of `0` to `300` and is declared in centi-dBm. Read your reader's regional ceiling with [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region); `maxTxPowerSupported` is declared in dBm. Confirm the setting's scale before comparing the two fields. Start low, stay within your region's rules, and confirm the power a setting produces before you rely on it. See [Improve Read Performance](/guides/read-tags-and-barcodes/improve-read-performance#the-regulatory-ceiling).
:::

The contract's full `ADVANCED` example is on the [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) reference page.

### Link Profiles {#link-profiles}

A link profile is the tag-to-reader side of the air interface: the backscatter encoding and the link
frequency. The contract's `linkProfile` values name both — `FM0` is FM0 baseband, `M2`, `M4` and `M8`
are Miller-2, Miller-4 and Miller-8, and the suffix is the backscatter link frequency.

**The trade is throughput against robustness.** Within a link frequency, a lower Miller order returns
tags faster and a higher one is more tolerant of noise, other readers and multipath. Zebra's RFD40/RFD90
read performance guide gives the tag reply rate of each family:

| Family | Tag reply rate | Where it sits |
|---|---|---|
| `FM0_320K` | 320 kbps | Fastest replies; least robust |
| `M2_320K` | 160 kbps | High throughput |
| `M2_256K` | 128 kbps | High throughput |
| `M2_240K` | 120 kbps | A conservative fast option |
| `M4_320K` | 80 kbps | Faster Miller-4 |
| `M4_256K` | 64 kbps | The dense-reader family |
| `M4_240K` | 60 kbps | The general baseline, and the first resilient family |
| `M8_320K` | 40 kbps | Advanced, difficult-link work |
| `M8_256K` | 32 kbps | Super dense |
| `M8_240K` | 30 kbps | Most robust, slowest |

`FM0_0K` is declared by the contract and names no link frequency; what it selects is not specified in
the available sources.

**Region decides which of these a reader will offer.** The guide gives one rule that accounts for it:
outside FCC configurations, a mode is available only if it uses Miller coding rather than FM0 and a
backscatter frequency of 320 kHz or below. In practice that means the 640 kHz families are FCC-only,
and FM0 is not available under standard ETSI. A reader's region, SKU and firmware together decide what
it offers, so confirm on the reader rather than assuming from this table. See
[RF Regions and Regulations](/resources/rf-regions-and-regulations).

**Two newer families are not reachable over MQTT.** Firmware `SAAFKS00-012-R00` added the `M2/640K`
and `M4/640K` link profiles, and the contract's `linkProfile` vocabulary has no 640K member, so
`set_operating_mode` cannot select them. See
[Known Issues and Open Questions](/resources/known-issues-and-open-questions#unsupported).

**Do not carry a number from a tool into a payload.** 123RFID and the SDK present RF modes by index,
0 to 39, and engineering material uses a separate link-profile identifier with different numbering.
The two are not interchangeable, and neither is what `linkProfile` accepts: this API takes the named
values above.

### What a Region Starts From {#regional-defaults}

A reader ships with a working configuration for its region, and a named profile that does not set an
RF mode leaves that default in place. The read performance guide records these defaults:

| Configuration | Default RF mode | What it means |
|---|---|---|
| Americas and many Asia-Pacific configurations | Mode 13, an `M4_240K` mode | A general-purpose setting |
| Europe and many EMEA configurations | Mode 19, an `M4_256K` mode | The same setting the dense-reader profile uses |
| Certain Japan 1 W listen-before-talk configurations | Mode 9, an `M2_256K` mode | Leans toward completing quickly, because listen-before-talk limits how long the reader may transmit |

In Europe and most EMEA configurations the regional default is already a dense-reader setting, so
selecting `DENSE_READERS` may leave the radio setting unchanged even though the profile's other
settings still change.

## Configure the Operating Mode {#configure-the-operating-mode}

### Tune the Gen2 Query {#query}

`query` sets the EPC Gen2 Query parameters for the inventory:

| Member | Values |
|---|---|
| `session` | `SESSION_0` to `SESSION_3` |
| `inventoryState` | `STATE_A`, `STATE_B`, or `STATE_AB`, which alternates between the two |
| `slFlag` | `ALL`, `ASSERTED` or `DEASSERTED`. `ASSERTED` and `DEASSERTED` are useful only with a `select` entry that changes the SL flag |
| `tagPopulation` | An estimate of the number of tags in the field, which helps the reader tune its inventory |

```json title="set_operating_mode — request (contract example: Query settings)"
{
  "command": "set_operating_mode",
  "requestId": "1286",
  "operatingMode": {
    "operatingModes": {
      "query": {
        "session": "SESSION_1",
        "inventoryState": "STATE_A",
        "slFlag": "ALL",
        "tagPopulation": 30
      }
    }
  }
}
```

How sessions behave on the air is explained in [How the Radio Reads Tags](/guides/core-concepts/how-the-radio-reads-tags).

### Pre-Filter with Select {#select}

`select` is a list of up to 32 Gen2 Select filters, applied before the inventory round. Each entry requires all seven members: `enable`, `tagPattern`, `memoryBank`, `offset`, `length`, `action` and `target`. `offset` and `length` count **bits**, and `tagPattern` is an even-length hex string of at most 64 characters.

```json title="set_operating_mode — request (contract example: Select settings)"
{
  "command": "set_operating_mode",
  "requestId": "1286",
  "operatingMode": {
    "operatingModes": {
      "select": [
        {
          "enable": true,
          "tagPattern": "2222EEEEFFFF1111AAAABBBB",
          "memoryBank": "EPC",
          "offset": 32,
          "action": "INV_B_NOT_INV_A_OR_DSRT_SL_NOT_ASRT_SL",
          "target": "SESSION_SL",
          "length": 16
        }
      ]
    }
  }
}
```

More than 32 entries returns code `24`, and a pattern that is too long returns code `28`. What the `action` and `target` values do is covered in [Pre-Filter Tags with Select](/guides/read-tags-and-barcodes/pre-filter-tags-with-select).

### Run Access Operations {#access-operations}

`accessOperations` is a list of operations the reader runs against every tag it reads. Each entry has an `operationType` and a `config`:

| `operationType` | Required in `config` |
|---|---|
| `READ` | `memoryBank`, `offset`, `length` |
| `WRITE` | `memoryBank`, `offset`, `length`, `data` |
| `ACCESS` | `password` |
| `LOCK` | `lockMemBank`, `lockAction` |
| `KILL` | `password` |

Here `offset` and `length` count **16-bit words**, not bits as in `select`. `data` is hex in whole 16-bit words, and `password` is exactly 8 hex characters.

:::danger[Some access operations cannot be undone]
`WRITE` changes tag memory. `KILL` permanently disables a tag, and `lockAction` values `PERMANENT_LOCK` and `PERMANENT_UNLOCK` cannot be reversed by any command. Because the operations run against every tag the reader reads, test them on a disposable set of tags, and put an explicit confirmation step in your application before you send them.
:::

```json title="set_operating_mode — request (contract example: Access operations)"
{
  "command": "set_operating_mode",
  "requestId": "1286",
  "operatingMode": {
    "operatingModes": {
      "accessOperations": [
        {
          "operationType": "READ",
          "config": {
            "memoryBank": "EPC",
            "offset": 2,
            "length": 3
          }
        },
        {
          "operationType": "READ",
          "config": {
            "memoryBank": "TID",
            "offset": 1,
            "length": 2
          }
        },
        {
          "operationType": "WRITE",
          "config": {
            "memoryBank": "USER",
            "offset": 2,
            "length": 2,
            "data": "FFFFEEEE",
            "password": "00000000"
          }
        },
        {
          "operationType": "ACCESS",
          "config": {
            "password": "00000000"
          }
        },
        {
          "operationType": "LOCK",
          "config": {
            "password": "00000000",
            "lockMemBank": "EPC",
            "lockAction": "UNLOCK"
          }
        }
      ]
    }
  }
}
```

The results arrive in each tag record's `accessResults`, one entry per configured operation, in order. Codes `31` and `32` report a write that is too long or whose data does not match its length. See [Read and Write Tag Memory](/guides/read-tags-and-barcodes/read-and-write-tag-memory).

### Choose the Tag Metadata {#tag-metadata}

`tagMetaDataToEnable` switches the optional fields of each tag record on and off. Fewer fields make each record smaller, so more records fit in the 6144-byte message limit.

```json title="set_operating_mode — request (contract example: Tag metadata settings)"
{
  "command": "set_operating_mode",
  "requestId": "1286",
  "operatingMode": {
    "operatingModes": {
      "tagMetaDataToEnable": {
        "RSSI": true,
        "PHASE": true,
        "SEENCOUNT": true,
        "CHANNEL": true,
        "PC": false,
        "EPC": true,
        "TID": false,
        "USER": false,
        "MAC": false,
        "HOSTNAME": false
      }
    }
  }
}
```

Which flag controls which field is covered in [Choose Which Tag Fields Are Reported](/guides/read-tags-and-barcodes/choose-tag-data-fields).

### Reporting Aggregation Is Not Settable {#aggregation}

The contract describes two shapes a tag record can take: every read reported on its own, with `seenCount` `1` and `channel` and `phase` present, or reads aggregated, with `seenCount` counting them and `channel` and `phase` absent. The current contract declares no `reportFilter` setting. Code for both shapes. How often the reader publishes is set by the endpoint's `batching` block; see [How Reads Become Messages](/guides/core-concepts/the-tag-data-stream#batching).
