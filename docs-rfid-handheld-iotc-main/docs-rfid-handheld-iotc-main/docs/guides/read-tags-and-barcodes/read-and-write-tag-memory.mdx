A reader can run access operations against the tags it reads: read or write a memory bank, open access with a password, lock memory, or kill a tag. You configure them in the `accessOperations` list of the operating mode, and the reader runs every operation in the list against **every tag it reads** during an inventory.

:::danger[Some operations cannot be undone]
`WRITE` changes tag memory. `KILL` permanently disables a tag, and the `lockAction` values `PERMANENT_LOCK` and `PERMANENT_UNLOCK` cannot be reversed by any command. Because the operations apply to every tag the reader reads, a destructive operation runs on every tag in the field. Test on a set of tags you can afford to lose, narrow the population with [pre-filters](/guides/read-tags-and-barcodes/pre-filter-tags-with-select), and put an explicit confirmation step in your application.
:::

## The Memory Banks {#memory-banks}

| Bank | Contents |
|---|---|
| `RESERVED` | The kill and access passwords |
| `EPC` | The CRC, the Protocol Control word and the EPC |
| `TID` | The factory-programmed tag identification |
| `USER` | Application data |

A `LOCK` addresses lockable resources rather than banks: `EPC`, `ACCESS_PWD`, `KILL_PWD`, `TID`, `USER` or `ALL`.

## The Operations {#operations}

Each entry has an `operationType` and a `config`:

| `operationType` | Required in `config` | What it does |
|---|---|---|
| `READ` | `memoryBank`, `offset`, `length` | Reads from a memory bank |
| `WRITE` | `memoryBank`, `offset`, `length`, `data` | Writes to a memory bank |
| `ACCESS` | `password` | Opens access with a password |
| `LOCK` | `lockMemBank`, `lockAction` | Locks or unlocks a resource |
| `KILL` | `password` | Permanently disables the tag |

- `offset` and `length` count **16-bit words**, not bits. The `offset` and `length` of a `select` pre-filter count bits.
- `data` is hex in whole 16-bit words: a multiple of four hex characters.
- `password` is exactly 8 hex characters, 32 bits.
- `lockAction` is `UNLOCK`, which makes the resource writable without a password; `READ_AND_WRITE`, which makes it accessible only with the access password; or `PERMANENT_LOCK` or `PERMANENT_UNLOCK`, which cannot be undone.

The contract states no limit on the number of access operations.

## Configure the Operations {#configure}

1. Stop any running inventory. The reader refuses `set_operating_mode` with code `11` while one runs.
2. Enable the metadata you need in the tag records, for example `TID` or `USER`. See [Choose Which Tag Fields Are Reported](/guides/read-tags-and-barcodes/choose-tag-data-fields).
3. Send [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) with the list. This contract example reads from the EPC and TID banks, writes the USER bank, opens access and unlocks the EPC bank:

   ```json title="set_operating_mode — request (contract example: Access operations)"
   {
     "command": "set_operating_mode",
     "requestId": "1286",
     "operatingMode": {
       "operatingModes": {
         "accessOperations": [
           {
             "operationType": "READ",
             "config": {
               "memoryBank": "EPC",
               "offset": 2,
               "length": 3
             }
           },
           {
             "operationType": "READ",
             "config": {
               "memoryBank": "TID",
               "offset": 1,
               "length": 2
             }
           },
           {
             "operationType": "WRITE",
             "config": {
               "memoryBank": "USER",
               "offset": 2,
               "length": 2,
               "data": "FFFFEEEE",
               "password": "00000000"
             }
           },
           {
             "operationType": "ACCESS",
             "config": {
               "password": "00000000"
             }
           },
           {
             "operationType": "LOCK",
             "config": {
               "password": "00000000",
               "lockMemBank": "EPC",
               "lockAction": "UNLOCK"
             }
           }
         ]
       }
     }
   }
   ```

   Replace the example passwords with your tags' passwords, and never commit real ones.

4. Check the reply:

   | Code | Meaning | What to do |
   |---|---|---|
   | `11` | Inventory in progress | Stop the inventory, then send again |
   | `23` | Invalid enum value | Correct the value from the enum on the reference page |
   | `31` | Max write length exceeded | Shorten `data`. The contract does not state the maximum |
   | `32` | Write data length mismatch | Make `data` match the `length` you declared |

5. Read the operating mode back with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode), then start an inventory.

## Read the Results {#results}

Each tag record carries `accessResults`: one string per configured operation, in the order you configured them. A successful read has the form `<OPERATION>-<MEMORY_BANK>-<RESULT>`; the contract also describes a successful operation as `SUCCESS`, and a failure as an error message. It declares no fixed list of results, so treat any value you do not recognize as a failure.

  "timestamp": "2026-06-16T06:17:41.088Z",

## Turn the Operations Off {#turn-off}

The operations keep running on every inventory until you change the operating mode. When the job is done, send `set_operating_mode` with the list you want next. How the reader treats an empty `accessOperations` list is not specified in the available sources, so read the mode back to confirm. The operating mode, including its access operations, is also lost on reboot.
