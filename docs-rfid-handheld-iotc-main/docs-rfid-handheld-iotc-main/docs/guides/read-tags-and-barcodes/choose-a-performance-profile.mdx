A profile is a named radio configuration. You choose one with the `profiles` member of the operating mode, sent with [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode). Choose it from the outcome you need, then test it where the reader actually works.

## Choose an Operating Mode {#choose-an-operating-mode}

| Profile | What the contract says it does | Use it when |
|---|---|---|
| `BALANCED_PERFORMANCE` | Balances performance and battery life. The reader uses it when no mode is configured | You need an everyday starting point |
| `CYCLE_COUNT` | Reads as many unique tags as possible | You are counting a large population of items |
| `DENSE_READERS` | Suits several readers in proximity | Other readers operate nearby |
| `OPTIMAL_BATTERY` | Gives the best battery life | Battery must last a long shift |
| `ADVANCED` | Uses the link profile, power and session you set in `advancedConfigurations` | No named profile meets the requirement |
| `FAST_READ` | Maximum read speed within short range | Do not use it: see below |

Do not rely on `FAST_READ` for a tag-data integration. Choose another profile from the table.

For every profile except `ADVANCED`, the reader chooses the link profile internally.

## What a Profile Changes {#what-a-profile-changes}

A profile is not one setting. Zebra's RFD40/RFD90 read performance guide describes each named
profile as a combination of four: transmit power, the Gen2 inventory session, Dynamic Power
Optimization, and the radio's RF mode.

| Profile | Transmit power | Session | Dynamic Power Optimization | RF mode |
|---|---|---|---|---|
| Fastest Read | 30 dBm | S0 | Off | Varies by region |
| `DENSE_READERS` | 30 dBm | See the guide | Off | A dense-reader mode, by region |
| `CYCLE_COUNT` | 30 dBm | S2 | Off | The regional default |
| `BALANCED_PERFORMANCE` | 27 dBm | S1 | On | The regional default |
| `OPTIMAL_BATTERY` | 24 dBm | S1 | On | The regional default |

Two things follow from that table, and they explain most of what people notice in the field:

- **Only two profiles change the radio's RF mode.** `CYCLE_COUNT`, `BALANCED_PERFORMANCE` and
  `OPTIMAL_BATTERY` keep the region's default mode and change power, session and DPO instead.
- **The named profiles differ in power by 6 dB**, from 30 dBm down to 24 dBm, which is the single
  largest influence on read distance and on battery drain.

**The session is the part that surprises people.** The session decides how long a tag stays quiet
after it answers:

| Session | After a tag is read | Suits |
|---|---|---|
| `SESSION_0` | It can answer again almost immediately | Confirming a few tags, or locating one item. Poor for large populations, because the nearest tags dominate |
| `SESSION_1` | It goes quiet briefly, then can answer again | General everyday work |
| `SESSION_2` | It stays quiet for as long as it remains in the field | Counting a large population once, which is why `CYCLE_COUNT` uses it |

The profile sets the session for you. Over MQTT you can also set it directly, as
`operatingModes.query.session`, which is how `ADVANCED` reaches the same control. See
[Configure Advanced Radio Settings](/guides/read-tags-and-barcodes/configure-advanced-radio-settings).

**The transmit-power figures above are the guide's, in dBm; the API's `transmitPower` is not in
dBm.** The API declares it in centi-dBm over 0 to 300. Confirm the applied power on your reader; do not
convert between the two. See [The Regulatory Ceiling](/guides/read-tags-and-barcodes/improve-read-performance#the-regulatory-ceiling).

No profile extends read range on its own. When tags are weak, distant or awkward to read, check the physical setup first: see [Improve Read Performance](/guides/read-tags-and-barcodes/improve-read-performance).

## Set a Profile {#set-a-profile}

1. Stop any running inventory. The reader refuses `set_operating_mode` with code `11` while one runs.
2. Send `set_operating_mode`. The profile sits two levels down, in `operatingMode.operatingModes`, and a partial update leaves the rest of the mode unchanged:

   ```json title="set_operating_mode — request (contract example: Profile setting)"
   {
     "command": "set_operating_mode",
     "requestId": "1286",
     "operatingMode": {
       "operatingModes": {
         "profiles": "BALANCED_PERFORMANCE"
       }
     }
   }
   ```

3. Check the reply. Success is code `0`, or no code with the description `Success`.
4. Read the mode back with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode):

   ```json title="get_operating_mode — request (contract example: Get operating mode)"
   {
     "command": "get_operating_mode",
     "requestId": "abc123"
   }
   ```

5. Re-apply the profile after every restart. The operating mode set with `set_operating_mode` is lost on reboot, and the reader returns to its default mode.

| Code | Meaning | What to do |
|---|---|---|
| `11` | Inventory in progress | Stop the inventory, then send the mode again |
| `22` | Advanced configuration not set | Send `advancedConfigurations` with `profiles: "ADVANCED"` |
| `23` | Invalid enum value | Correct the value from the enum on the reference page |
| `24` | Max 32 prefilters limit exceeded | Send at most 32 `select` entries |
| `28` | Tag match pattern length exceeded | Shorten the pattern |
| `31` | Max write length exceeded | Shorten the data in the access operation |
| `32` | Write data length mismatch | Make the data match the declared length |

## Configure the `ADVANCED` Profile {#advanced}

`profiles: "ADVANCED"` requires `advancedConfigurations`; without it the reply is code `22`. The block holds four settings:

| Member | Meaning |
|---|---|
| `transmitPower` | The transmit power, declared from `0` to `300`. The unit is unresolved: see the caution below |
| `linkProfile` | The air-interface link profile. Eleven values, such as `M2_240K` for Miller-2 at 240 kHz. Higher Miller orders are more robust with many readers and multipath; faster profiles read more tags per second |
| `session` | The EPC Gen2 session, `SESSION_0` to `SESSION_3`. `query.session` sets the same thing, and the contract does not say which wins if you send both |
| `dynamicPower` | `true` lets the radio adjust transmit power during an inventory. Whether `transmitPower` is then a ceiling or a starting point is not documented |

:::caution[Confirm the applied transmit power]
`transmitPower` has a range of `0` to `300` and is declared in centi-dBm. Read your reader's regional ceiling with [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region); `maxTxPowerSupported` is declared in dBm. Confirm the setting's scale before comparing the two fields. Start low, stay within your region's rules, and confirm the power a setting produces before you rely on it. See [Improve Read Performance](/guides/read-tags-and-barcodes/improve-read-performance#the-regulatory-ceiling).
:::

The contract's full `ADVANCED` example, which also sets access operations, pre-filters and metadata, is on the [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) reference page. More on the advanced settings is in [Configure Advanced Radio Settings](/guides/read-tags-and-barcodes/configure-advanced-radio-settings).

## Test the Choice {#test}

A profile is a starting point. Run an inventory where the reader works, compare the tags you read with the tags you expect, and change one setting at a time. See [Test and Validate Performance](/guides/read-tags-and-barcodes/improve-read-performance#test-and-validate-performance).
