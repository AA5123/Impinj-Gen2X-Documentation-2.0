Provisioning a group of readers means bootstrapping each one once, then applying the same baseline configuration to all of them over MQTT, one configuration domain at a time. This page works through three readers. The same steps apply to more; only your tooling changes.

## Before You Begin {#before-you-begin}

- The broker side exists: a reachable broker, credentials for each reader, and access rules. See [Cloud Integrations](/guides/build-your-integration/plan-your-integration#cloud-integrations).
- You have decided the baseline: the endpoints, Wi-Fi profiles, certificates, event reporting, operating mode and post-filters every reader should have. Write it down as a file per domain, in version control.
- Your provisioning tool is subscribed to the management topics of all three readers, for example `acme/MDM/clients/resp/+` and `acme/MDM/clients/event/+`.

## Step 1: Bootstrap Each Reader {#bootstrap}

Bootstrap each reader with 123RFID Desktop: the region, a Wi-Fi profile and a first MQTT endpoint, with the same tenant ID and topic conventions on every reader. See [Bootstrap a Reader with 123RFID Desktop](/guides/manage-your-reader/bootstrap-reader).

Confirm each reader over MQTT with [`get_version`](/api-reference/mqtt/mgmt/get-version), and record its serial number and firmware version.

## Step 2: Apply the Baseline, Domain by Domain {#apply-baseline}

There is no command that writes a whole configuration, so apply each domain with its own command, in an order where each step depends only on earlier ones:

| Order | Domain | Command | Notes |
|---|---|---|---|
| 1 | Certificates | [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate) | Asynchronous: wait for `SAVE SUCCESS` before an endpoint uses the certificate |
| 2 | Wi-Fi profiles | [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi) | Save with `connect: false` unless you mean to switch networks |
| 3 | Endpoints | [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) | A data endpoint's tag-data topic goes in the second publish position |
| 4 | Event reporting | [`config_events`](/api-reference/mqtt/mgmt/config-events) | Takes effect after a reboot |
| 5 | Operating mode | [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) | Lost on reboot: apply it after any restart |
| 6 | Post-filters | [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter) | One rule per request |

For example, enable the heartbeat on each reader. The interval is in seconds, at most 65,535:

```json title="config_events — request (illustrative: heartbeat settings only)"
{
  "command": "config_events",
  "requestId": "abc123",
  "eventConfiguration": {
    "heartbeat": true,
    "heartbeatConfiguration": {
      "interval": 100,
      "inventoryStatus": true,
      "batteryStatus": true
    }
  }
}
```

Give each command its own `requestId`, check each reply before the next step, and follow the asynchronous ones to their outcome; see [Track Asynchronous Commands](/guides/build-your-integration/track-asynchronous-commands). Do not send all the commands at once: the reader queues at most 10.

After the endpoint and event steps, restart each reader with [`reboot`](/api-reference/mqtt/mgmt/reboot) so the event settings apply, wait for its `CONNECTED` `mqttConnEVT`, then apply the operating mode.

## Step 3: Verify Each Reader {#verify}

Read each domain back and compare it with the baseline:

| Domain | Read it with |
|---|---|
| Endpoints | `get_endpoint_config` |
| Wi-Fi profiles | `get_wifi` |
| Certificates | `get_installed_certificates` |
| Operating mode | `get_operating_mode` |
| Post-filters | `get_post_filter` |
| Event reporting | `eventConfiguration` in `get_endpoint_config`; also confirm that `heartBeatEVT` and the alerts you enabled arrive |

**Checkpoint:** every reader matches the baseline in each readable domain, and `heartBeatEVT` arrives from all three, for example on `acme/MDM/clients/event/+`. How to compare and correct is in [Keep Configuration Consistent](/guides/scale-to-a-fleet/keep-configuration-consistent).

## Automate Provisioning {#automate-provisioning}

Once the steps work by hand, script them:

1. **Detect new readers.** Subscribe to the connection-state topics of the tenant with a wildcard, for example `acme/MDM/clients/rfid/+`, and treat a `CONNECTED` `mqttConnEVT` from an unknown serial number as a reader to provision.
2. **Apply the baseline** from version control, domain by domain, in the order above.
3. **Verify** by reading each domain back.
4. **Record the result** per reader: its serial number, firmware version, baseline version and when it was verified.

```python
def on_connection_event(topic: str, event: dict) -> None:
    serial = topic.rsplit("/", 1)[-1]          # the reader appends its serial number
    if event.get("connectionState") == "CONNECTED" and serial not in known_readers:
        schedule_provisioning(serial)          # apply the baseline domain by domain, then verify
```

This sketch is illustrative and has not been run against a reader. Keep the baseline files in version control, test a change on one reader before you provision with it, and roll changes to existing readers out in stages; see [Roll Out Changes in Stages](/guides/scale-to-a-fleet/roll-out-changes-in-stages).

Whether 123RFID Desktop can bootstrap several readers in one session is not specified in the available sources.
