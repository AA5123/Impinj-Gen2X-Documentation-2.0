A change that reaches every reader at once can take the whole fleet off the network, and a reader that loses its only MQTT connection needs 123RFID Desktop to recover. Roll firmware and configuration changes out in stages instead: a few readers first, then more, with a check between each stage.

## Before You Begin {#before-you-begin}

1. **Capture a baseline** for every reader in scope: read each configuration domain and record the result, together with `get_version`. See [Keep Configuration Consistent](/guides/scale-to-a-fleet/keep-configuration-consistent#snapshot). The baseline is what you compare with after each stage, and what you restore from if a reader must be bootstrapped again.
2. **Choose cohorts.** Start with a small group of readers you can reach physically, then widen. Put readers from each site, model and firmware version in the early cohorts, so that a problem specific to one of them shows up early.
3. **Agree the gates** before you start: what you check after each stage, how long you wait, and what stops the rollout.
4. **Write down the recovery path.** For a reader left without an MQTT connection, recovery is 123RFID Desktop over USB-C, then the baseline re-applied over MQTT.

For a firmware change, also check:

- The firmware URL is reachable from each reader's own network, not only from your workstation.
- The readers are charged or on external power; a low battery refuses the update with code `14`.
- The readers have free flash; too little refuses the update with code `8`.

Whether `set_os` can install an older image than the one running is not specified in the available sources. Plan a firmware change as if it cannot be undone.

## Execute a Phased Migration {#execute-a-phased-migration}

### 1. Push the Change to a Stage {#push}

For a firmware change, send [`set_os`](/api-reference/mqtt/mgmt/set-os) to each reader in the stage:

```json title="set_os — request (adapted from contract example: Pre-installed CA certificate HTTPS; addresses replaced with fictional ones, verificationType set to VERIFY_HOST_AND_PEER)"
{
  "command": "set_os",
  "requestId": "abc124",
  "OSUpdateDetails": {
    "url": "https://192.0.2.39:8000/Build-3.10.27/Firmware/PAAFKS00-013-R01E0.DAT",
    "authenticationType": "CERTIFICATE",
    "verificationType": "VERIFY_HOST_AND_PEER",
    "caCertificateFile": "filestore_ca_cert"
  }
}
```

The reply is code `1`: the update has started. Follow each reader's `FIRMWARE_UPDATE` alerts until `updateStatus` equals `FW update success`, then confirm with `get_version`. See [Update Firmware and Restart the Reader](/guides/manage-your-reader/update-firmware-and-restart). Pace the commands: every reader downloads the image from your server.

For a configuration change, send the per-domain commands to each reader in the stage, and check each reply before the next.

### 2. Widen Stage by Stage {#waves}

An example plan:

| Stage | Share of the fleet | Wait before the next stage |
|---|---:|---|
| 1 | A handful of readers you can reach | Long enough to cover a full working shift |
| 2 | About a tenth | A working shift |
| 3 | About half | A working shift |
| 4 | The rest | — |

Adjust the sizes and waits to your fleet and risk. Promote a stage only when it passes the checks in [Verify a Migration](#verify-a-migration).

### 3. Know Your Rollback Triggers {#3-know-your-rollback-triggers}

Stop promoting stages if the current stage shows any of these:

- Readers that do not reconnect: no `CONNECTED` `mqttConnEVT` and no `heartBeatEVT` within the window you agreed.
- A rise in `alerts` that follows the change.
- A firmware update that does not reach `FW update success`, or a `get_version` that does not show the target.
- Configuration that differs from the baseline in a way the change did not intend.

Rolling back means stopping the rollout, then recovering the readers in a bad state: over MQTT where you still have a connection, or with 123RFID Desktop and the baseline where you do not.

### 4. Handle Readers That Were Offline {#stragglers}

Some readers will be switched off or out of range when their stage runs. Do not hold the rollout for them. Track them as a separate group, and apply the change when each one next sends a `CONNECTED` `mqttConnEVT`.

## Verify a Migration {#verify-a-migration}

After each stage, check every reader in it:

1. **Firmware.** [`get_version`](/api-reference/mqtt/mgmt/get-version) shows the target `firmwareVersion` and `detailedVersions`. A reader still on the old version did not take the update; treat it as outstanding, not as a pass.
2. **Configuration.** Read each domain and compare it with the baseline. Code `3` means the reader could not gather the information at that moment; read it again before you flag the reader. Whether a firmware update keeps endpoints, Wi-Fi profiles, certificates and post-filters is not specified in the available sources, so compare them all.
3. **Operating mode.** A restart returns the reader to its default operating mode. If the update restarted the reader, re-apply the mode with [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) and confirm it with [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode).
4. **Behavior in service.** Watch `heartBeatEVT` and `alerts` over the agreed wait, and compare the alert rate with the time before the change.

Declare the stage complete only when every reader in it is on the target, matches the baseline except for what you meant to change, and behaves normally in service. If any check fails, stop and follow the [rollback triggers](#3-know-your-rollback-triggers).
