A reader's configuration drifts from what you intended: a restart resets its operating mode, a change fails half-way, someone changes a reader with 123RFID Desktop. This page shows how to find the differences and correct them. The MQTT API has no command that reads or writes a whole configuration, so both steps work one domain at a time.

## What You Can Check {#domains}

| Domain | Read | Correct with |
|---|---|---|
| Endpoints | [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) | [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) |
| Wi-Fi profiles | [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi) | [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi), [`delete_wifi_profile`](/api-reference/mqtt/mgmt/delete-wifi-profile) |
| Certificates | [`get_installed_certificates`](/api-reference/mqtt/mgmt/get-installed-certificates) | [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate), [`delete_certificate`](/api-reference/mqtt/mgmt/delete-certificate) |
| Operating mode | [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode) | [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) |
| Post-filters | [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter) | [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter) |
| Firmware | [`get_version`](/api-reference/mqtt/mgmt/get-version) | [`set_os`](/api-reference/mqtt/mgmt/set-os) |
| Event reporting | `eventConfiguration` in [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) | [`config_events`](/api-reference/mqtt/mgmt/config-events) |

`config_events` has no read command of its own. Its settings show in the `eventConfiguration` block of each active endpoint's read-back, for example `heartbeatConfiguration` appears there only after `config_events` has enabled the heartbeat. The contract also describes that block as a separate, per-endpoint setting and does not say which of the two wins, so check event reporting by its effect as well: the heartbeats and alerts you enabled arrive.

## Store a Baseline {#baseline}

Keep the intended configuration in version control, one file per domain, in whatever format your tooling uses. Record only the settings you intend, not what a reader reports about its state:

- **Include:** endpoint names, types, brokers, ports, protocols, verification types and topics; Wi-Fi network names, security types and preference; installed certificate names and types; the operating mode; the post-filter rules; the firmware version.
- **Leave out:** addresses from DHCP, `status` fields, battery and temperature readings, `radioActivity`, and anything else that changes while the reader runs.

Change the baseline through the same review you use for code. A comparison is only as trustworthy as the baseline it compares with.

## Detect and Remediate Drift {#detect-and-remediate-drift}

### Step 1: Snapshot Each Reader {#snapshot}

For each reader, send each read command and keep the reply. Before you use a reply, check its code:

- **Success** (code `0`, or no code with the description `Success`): the snapshot of that domain is valid.
- **Code `3`**: the reader could not gather the information at that moment. Mark the domain unknown and read it again later.
- **Code `4`**: a firmware update is running; every command is refused until it ends.
- **No reply**: the reader, its session or the path may be down. Check its recent `heartBeatEVT` before you conclude anything about its configuration.

A domain you could not read is unknown, not unchanged.

### Step 2: Compare with the Baseline {#compare}

Compare each domain with the baseline, field by field, and classify each difference:

| Difference in | Treat it as | Why |
|---|---|---|
| Operating mode, post-filters | Correct it automatically | Low risk. The operating mode is expected to differ after every restart, because a restart returns the reader to its default mode |
| Endpoint brokers, ports, TLS settings, certificates, Wi-Fi networks, firmware | Raise it for a person to review | A wrong change can cut the reader's only connection, and the fix then needs 123RFID Desktop |

A difference that returns on the same field every time points at something re-applying an old setting upstream, not at the reader.

### Step 3: Correct the Differences {#correct}

Correct each domain with its own command, and only the fields that differ. Keep the reader's rules in mind:

- **Operating mode.** Stop any inventory first; the reader refuses `set_operating_mode` with code `11` during one. A partial update changes only what you send.
- **Post-filters.** One rule per request. A rule has no identifier of its own, so send its members exactly as they are installed when you modify or delete it.
- **Endpoints.** The reader refuses to modify an active endpoint and returns code `35`. Correct an endpoint through the staged procedure in [Configure MQTT Endpoints](/guides/manage-your-reader/configure-mqtt-endpoints#stage-and-activate), over a different management endpoint.
- **Wi-Fi.** Use `MODIFY` for a profile that exists; `CREATE` on an existing network returns code `18`.

Give each corrective command a new `requestId`. See [Retry Commands Safely](/guides/build-your-integration/retry-commands-safely).

### Step 4: Confirm Convergence {#confirm}

A code `0` reply means the reader accepted the change, not that the reader now matches the baseline. Read the domain again and compare it again. Only a clean comparison closes the difference.

## Run the Check on a Schedule {#schedule}

- **After every restart**, re-apply the operating mode. Watch for `CONNECTED` `mqttConnEVT`, then read the operating mode and correct it.
- **Periodically**, snapshot every domain. How often is your choice: each snapshot is one command per domain per reader, and the reader queues at most 10 commands, so pace them.
- **Record** each run per reader: the differences found, the action taken, and whether the reader converged.
