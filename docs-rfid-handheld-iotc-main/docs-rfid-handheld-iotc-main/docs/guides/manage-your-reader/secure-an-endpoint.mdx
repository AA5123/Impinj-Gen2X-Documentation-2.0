A reader bootstrapped over plain MQTT on port `1883` sends its commands, replies, events and credentials unencrypted. This page moves that traffic to TLS on port `8883` without losing your connection to the reader. What each protection defends against is explained in [The Security Model](/guides/core-concepts/the-security-model).

The reader refuses to change an active endpoint and returns code `35`, so you cannot switch the endpoint you are using to TLS in place. Instead, add a TLS endpoint beside it, confirm the new one, and then retire the plain one.

## Before You Begin {#before-you-begin}

- Your broker has a TLS listener, usually on port `8883`, with a certificate that chains to a CA you hold in PEM form.
- For mutual TLS, you have a client certificate and a PKCS1 private key for the reader. See [Prepare the Certificate Material](/guides/manage-your-reader/install-and-manage-certificates#certificate-format-and-size).
- You are subscribed to the plain endpoint's response and event topics, and `fileDownload` event reporting is enabled.
- Plan a way back. If the plain endpoint is your only management connection and something goes wrong after you retire it, the fix needs 123RFID Desktop over USB-C.

## Step 1: Install the Certificates {#1-install-the-brokers-ca-certificate}

Install the broker CA, and for mutual TLS the client certificate and key, with [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate) and `type: "mqtt"`. One request can carry all three components:

```json title="install_certificate — request (adapted from contract example: MQTT certificates without authentication; addresses replaced with fictional ones)"
{
  "command": "install_certificate",
  "requestId": "19001",
  "certDetails": {
    "name": "mqtt_certs",
    "type": "mqtt",
    "authenticationType": "NONE",
    "certSource": "HTTP",
    "url": [
      {
        "key": "client_cert",
        "value": "https://192.0.2.107:8080/mqtt_client_cert.pem"
      },
      {
        "key": "client_key",
        "value": "https://192.0.2.107:8080/mqtt_client_key.pem"
      },
      {
        "key": "ca_cert",
        "value": "https://192.0.2.107:8080/mqtt_ca_cert.pem"
      }
    ],
    "verificationType": "VERIFY_HOST_AND_PEER"
  }
}
```

The reply is code `1`: the request was accepted, and the outcome comes later. Wait for the `alerts` event with `id: "FILE_DOWNLOAD"` and `fileType: "FILE_TYPE_CERT"` to report `DOWNLOAD SUCCESS` and then `SAVE SUCCESS`. `DOWNLOAD FAIL` means the reader could not fetch a file; `SAVE FAIL` means it fetched one but did not store it. Do not configure the endpoint until the install has succeeded. Then read [`get_installed_certificates`](/api-reference/mqtt/mgmt/get-installed-certificates) to see what is installed.

## Step 2: Add a TLS Endpoint {#add-tls-endpoint}

Before you add it, subscribe, over your broker's TLS listener, to the new endpoint's connection-state topic: its `publishTopics[2]`, `<tenantId>/MGMT/clients/rfid/<deviceSerialNumber>` in the example. The reader connects when it activates the endpoint, without a reboot, so subscribe first or you can miss the event.

Add a new endpoint with `protocol: "MQTT_TLS"`, the broker's TLS port, and `securityParams` naming the installed certificates. Give it a name of its own, because the plain endpoint keeps its name until you retire it. This example adds a management endpoint over TLS:

```json title="config_endpoint — request (illustrative: Add MGMT endpoint for MQTT TLS; addresses replaced with fictional ones)"
{
  "command": "config_endpoint",
  "requestId": "1233",
  "epConfig": {
    "operation": "add",
    "configuration": {
      "endpointName": "mgmt_tls",
      "epType": "MGMT",
      "protocol": "MQTT_TLS",
      "activate": true,
      "url": "broker.example.com",
      "port": 8883,
      "verificationType": "VERIFY_HOST_AND_PEER",
      "qosCommon": 1,
      "tenantId": "ZEBRA",
      "mqttParams": {
        "keepAlive": 300,
        "cleanSession": true,
        "reconnectDelayMin": 5,
        "reconnectDelayMax": 60,
        "publishTopics": [
          {
            "topic": "MGMT/clients/resp",
            "qos": 1,
            "retain": false
          },
          {
            "topic": "MGMT/clients/event",
            "qos": 1,
            "retain": false
          },
          {
            "topic": "MGMT/clients/rfid",
            "qos": 0,
            "retain": true
          }
        ],
        "subscribeTopics": [
          {
            "topic": "MGMT/clients/cmnd",
            "qos": 0,
            "retain": false
          }
        ]
      },
      "securityParams": {
        "format": "PEM",
        "caCertificateFile": "mqtt_ca_cert",
        "clientCert": "mqtt_client_cert",
        "clientKey": "mqtt_client_key"
      }
    }
  }
}
```

- For one-way TLS, where only the broker is authenticated, send `caCertificateFile` without `clientCert` and `clientKey`.
- The example adds the endpoint already active. To stage it instead, send `activate: false` and activate it later with an `update`. See [Stage an Endpoint, Then Activate It](/guides/manage-your-reader/configure-mqtt-endpoints#stage-and-activate).
- If the new endpoint uses different topic middle segments from the plain one, your application must subscribe to them. The same middle segments on the same broker and tenant produce the same topics.

A code `0` reply means the configuration was accepted, not that the TLS connection works.

## Step 3: Confirm the TLS Connection {#confirm}

1. On the connection-state topic you subscribed to in step 2, wait for `mqttConnEVT` with `connectionState: "CONNECTED"`:

   ```json title="mqttConnEVT — event (contract example: Connected event)"
   {
     "connectionState": "CONNECTED",
     "timestamp": "2026-06-15T13:09:33.810Z",
     "deviceModel": "RFD40",
     "deviceSerialNo": "RFD40-211545201D0034",
     "apiVersion": 1.21,
     "mqttVersion": 3.0999999
   }
   ```

   Current firmware sends `mqttVersion` as the number `3.0999999`, meaning MQTT 3.1.1, so never compare it for equality.

2. Send [`get_version`](/api-reference/mqtt/mgmt/get-version) on the new endpoint's command topic and check that the reply arrives on its response topic.

The contract specifies no time for the connection to come up; it depends on your network, the TLS handshake and the endpoint's reconnect delays. If `CONNECTED` does not arrive, the plain endpoint is still there: see [If It Does Not Work](#didnt-work).

## Step 4: Retire the Plain Endpoint {#retire-plain}

Over the new TLS endpoint, deactivate the plain endpoint, or delete it with `operation: "delete"`. From then on the reader's management traffic goes only over TLS. Check with [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) that only the TLS endpoint is active for that role.

## Choose the Verification Level {#verification-levels}

`verificationType` sets how far the reader checks the broker's certificate:

| `verificationType` | The reader checks |
|---|---|
| `VERIFY_HOST_AND_PEER` | The certificate chain and that the certificate matches the broker host |
| `VERIFY_NONE` | Nothing: the connection is encrypted, but the broker is not authenticated |

Use `VERIFY_HOST_AND_PEER` in production. The contract states that `VERIFY_NONE` must not be used there.

## If It Does Not Work {#didnt-work}

- **The handshake is rejected.** Check that the broker's certificate chains to the CA you installed, including any intermediate certificates, and that `securityParams` names the certificates you installed. With `VERIFY_HOST_AND_PEER`, the certificate must also match the host in `url`.
- **The certificate looks valid but is refused.** Certificate validity is checked against the reader's clock. [`get_status`](/api-reference/mqtt/mgmt/get-status) reports the reader's `systemTime` and `ntp.offset`.
- **`protocol` and `port` disagree.** The reader does not cross-check them. `MQTT_TLS` needs the broker's TLS port.

## Roll Back {#roll-back}

- **The plain endpoint is still active.** Delete the TLS endpoint over the plain one, fix the cause, and start again from step 2. The installed certificates stay in place, so you do not need to repeat step 1.
- **You already retired the plain endpoint and the reader does not come back.** There is no MQTT path left. Connect the reader to 123RFID Desktop over USB-C and restore an endpoint; see [RP-01: Connect a Sled to 123RFID Desktop](/guides/diagnose-and-recover/recovery-playbooks/reconnect-the-reader#rp-01) and [Bootstrap a Reader with 123RFID Desktop](/guides/manage-your-reader/bootstrap-reader).

## Harden the Connection {#harden}

These are general TLS practices, not reader features:

- **Set the protocol policy on the broker.** The reader is the TLS client, so TLS versions and cipher suites are enforced by the broker's listener.
- **Install the whole chain.** Give the reader the CA that signed the broker's certificate, and make sure the broker sends any intermediate certificates.
- **Keep private keys private.** Do not share one client key across unrelated readers or environments, and generate a new key when you replace a certificate. The reader accepts RSA keys in PKCS1 form only.
- **Watch expiry.** No event warns of an expiring certificate. Read `validTill` from `get_installed_certificates` on a schedule; see [Install and Manage Certificates](/guides/manage-your-reader/install-and-manage-certificates#list).
