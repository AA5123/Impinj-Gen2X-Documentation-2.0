Three read commands tell you what a reader is and what state it is in. None of them changes anything, and each is safe to send again. Send them to the management endpoint's command topic, for example `<tenantId>/MGMT/clients/cmnd/<deviceSerialNumber>`, and read the reply on its response topic.

| To find out | Send | Read |
|---|---|---|
| Which reader this is and what firmware it runs | [`get_version`](/api-reference/mqtt/mgmt/get-version) | `readerVersion` |
| Its power, battery, radio and clock state | [`get_status`](/api-reference/mqtt/mgmt/get-status) | `deviceStatus` |
| Which regulatory region it operates in | [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region) | `currentRegion` |

## Read the Reader's Identity {#identity}

1. Publish `get_version` with a new `requestId`:

   ```json title="get_version — request"
   {
     "command": "get_version",
     "requestId": "abc123"
   }
   ```

2. Check that `response.code` is `0`, then read `readerVersion`:

   ```json title="get_version — response (contract example: Device version info)"
   {
     "command": "get_version",
     "requestId": "abc123",
     "apiVersion": "V1.21",
     "readerVersion": {
       "firmwareVersion": "PAAFKS00-013-N05",
       "model": "RFD40",
       "serialNumber": "211545201D0034",
       "sku": "RFD4031-G10B700-US",
       "companyName": "Zebra Technologies",
       "manufacturerName": "Zebra Technologies",
       "detailedVersions": {
         "scannerFirmware": "PAAEOC20-003-R01",
         "radioFirmware": "2.0.53.0",
         "iotcVersion": "V1.22"
       }
     },
     "response": {
       "code": 0,
       "description": "Success"
     }
   }
   ```

- `model` is `RFD40` or `RFD90`.
- `serialNumber` is the reader's serial number. The contract directs clients to use the model-prefixed form, `model`, a hyphen and `serialNumber`, such as `RFD40-211545201D0034`. Subscribe with `+` in the serial position to match every reader.
- `sku` encodes the model, configuration and regulatory region.
- `firmwareVersion` is the top-level firmware build, and `detailedVersions` gives the scanner firmware, the radio firmware and `iotcVersion`, the IoT Connector version.

`get_version` does not depend on the radio's state, so it is a good first command after a reader connects or reconnects. It is also how you confirm a firmware update; see [Update Firmware and Restart the Reader](/guides/manage-your-reader/update-firmware-and-restart).

## Read the Reader's Runtime Status {#status}

1. Publish `get_status`:

   ```json title="get_status — request"
   {
     "command": "get_status",
     "requestId": "abcd123"
   }
   ```

2. Check `response.code`. Code `3` means the reader could not gather the information at that moment; retry after a short delay, and reboot the reader if it persists.
3. Read `deviceStatus`:

   ```json title="get_status — response (contract example: Device status info)"
   {
     "command": "get_status",
     "requestId": "abcd123",
     "apiVersion": "V1.21",
     "deviceStatus": {
       "powerSource": "USB",
       "radioActivity": "INACTIVE",
       "radioConnection": "DISCONNECTED",
       "systemTime": "2026-06-15T09:26:00.443Z",
       "ntp": {
         "offset": 0,
         "reach": 0
       },
       "terminalConnection": {
         "status": "CONNECTED",
         "type": "USB"
       },
       "batteryStatus": {
         "mfgDate": "22DEC2024",
         "cycleCount": 8,
         "fullChargeCapacity": 5739,
         "temperature": 24,
         "designCapacity": 6400,
         "batteryType": "LI-ION",
         "capacity": 2467,
         "stateOfHealth": "GOOD",
         "chargePercentage": 46,
         "chargeStatus": 1
       }
     },
     "response": {
       "code": 0,
       "description": "Success"
     }
   }
   ```

| Field | What it tells you |
|---|---|
| `powerSource` | `WALLCHARGER`, `USB` or `CRADLE` in the `get_status` enum; the `alerts` power event uses `BATTERY`, `USB`, `CRADLE` and `WALL_CHARGER`. Current firmware reports `CRADLE`, `USB` or `NONE`; `NONE` means no external power is attached. Accept all of them |
| `radioActivity` | `ACTIVE` while the RFID radio is performing an operation, otherwise `INACTIVE` |
| `radioConnection` | Whether the RFID radio module is attached and reachable, as distinct from whether it is working |
| `systemTime` | The reader's clock, in ISO 8601. Compare it with `ntp.offset`, in milliseconds, to judge synchronization |
| `terminalConnection` | Whether a host terminal is connected, and over `BLUETOOTH`, `CIO` or `USB` |
| `batteryStatus.chargePercentage` | Charge remaining, 0 to 100 |
| `batteryStatus.stateOfHealth` | `GOOD`, `MODERATE` or `CRITICAL`: how far the battery's capacity has degraded |
| `batteryStatus.chargeStatus` | `0` charger not connected, `1` charging, `2` charger connected and battery full |

`powerSource`, `radioActivity`, `radioConnection` and `systemTime` are always present; the other members can be absent. Check `radioActivity` before a change that is refused while the radio is working: `reboot` returns code `5` and `set_operating_mode` returns code `11` during an inventory. See [The Configuration Model](/guides/core-concepts/the-configuration-model#refusals).

For battery trends across a fleet, see [Monitor Reader Health and Battery](/guides/operate-and-monitor/monitor-reader-health-and-battery).

## Read the Regulatory Region {#region}

The region decides which frequencies the radio may use and at what power. No MQTT command changes it; the [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region) reference page names [123RFID Desktop](/resources/setup-tools) as the tool that sets it.

1. Publish `get_current_region`:

   ```json title="get_current_region — request"
   {
     "command": "get_current_region",
     "requestId": "abc123"
   }
   ```

2. Check `response.code`, then read `currentRegion`:

   ```json title="get_current_region — response (contract example: Current region info)"

       "regulatoryStandard": "FCC"
     },
     "response": {
       "code": 0,
       "description": "Success"
     }
   }
   ```

Several of these values are not settled in the contract. Read them, but do not build logic on their exact form:

- **`country`** is free text. The contract records both `USA` and `United States` for the same country.
- **`regulatoryStandard`** is free text with no fixed list. The contract shows both `FCC` and `FCC_USA`.
- **`channelData`** lists channel frequencies as strings. The contract does not state the unit; its example lists 50 United States channels such as `915750`, which read as kHz.
- **`maxTxPowerSupported`** and **`minTxPowerSupported`** are declared in dBm; the contract's example gives a maximum of `30`. The `transmitPower` you send with `set_operating_mode` is on a different scale; see [Improve Read Performance](/guides/read-tags-and-barcodes/improve-read-performance).

## Read the Network Interfaces {#network}

[`get_wifi`](/api-reference/mqtt/mgmt/get-wifi) reports the Wi-Fi profiles and the connected network, and [`get_eth`](/api-reference/mqtt/mgmt/get-eth) reports the Ethernet interface. See [Configure Wi-Fi](/guides/manage-your-reader/configure-wi-fi).
