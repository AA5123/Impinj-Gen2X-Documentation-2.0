An endpoint is a named MQTT connection configuration stored on the reader. This page shows how to inspect the endpoints a reader has, add new ones, activate them, change them and remove them. The concepts behind endpoint types and topic slots are in [Endpoints, Topics, and Channels](/guides/core-concepts/endpoints-topics-and-channels).

## Before You Begin {#before-you-begin}

- The reader has an active management connection you can send commands over, such as the MDM endpoint created in [Bootstrap a Reader with 123RFID Desktop](/guides/manage-your-reader/bootstrap-reader).
- Your application is subscribed to that endpoint's response topic, for example `<tenantId>/MDM/clients/resp/<deviceSerialNumber>`, before you publish.
- For a TLS endpoint, the certificates it names are installed. See [Install and Manage Certificates](/guides/manage-your-reader/install-and-manage-certificates).

## Choose How to Split Traffic {#choose-a-layout}

One endpoint can carry commands, replies, events and connection state. Tag data can also go to a management or control endpoint, where it arrives on that endpoint's `rfid` topic, but the contract calls that the fallback placement and recommends a dedicated `DATA1` endpoint for sustained inventory. `DATA2` is currently not supported.

Each endpoint opens its own MQTT session and has its own broker address, credentials and TLS settings. Split traffic across endpoints when you need one of these:

- Tag data on a different broker from management traffic.
- Different credentials or broker access rules for each class of traffic.

### Trade-Offs {#trade-offs}

| | One endpoint | Several endpoints |
|---|---|---|
| Credentials and certificates | One set | One set per endpoint, each to rotate |
| Connection state | One `mqttConnEVT` stream | One per endpoint |
| When a broker is unreachable | All traffic stops | Only that endpoint's traffic stops |
| Tag data | Shares a topic tree with connection-state events | Isolated on its own topics |

## Filter the Tags a Data Endpoint Reports {#filter-data-endpoint}

The contract declares two data endpoint types, `DATA1` and `DATA2`, but `DATA2` is currently not supported, so tag data goes to one `DATA1` endpoint. To limit which tags it reports, add a post-filter rule with [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter). Its `dataEpType` names the endpoint: `DATA_EP1` for `DATA1`.

```json title="set_post_filter — request (contract example: Filter tags using prefix)"
{
  "command": "set_post_filter",
  "requestId": "abc123",
  "postFilterPayload": {
    "operation": "ADD",
    "dataEpType": "DATA_EP1",
    "matchPattern": "FFFFBBBBA500",
    "matchPatternMethod": "PREFIX",
    "reportOperation": "INCLUDE"
  }
}
```

How often the data endpoint publishes is set by its `batching` block. See [How Reads Become Messages](/guides/core-concepts/the-tag-data-stream#batching) and [Post-Filter Reported Tags](/guides/read-tags-and-barcodes/post-filter-reported-tags).

## Inspect the Current Endpoints {#inspect}

1. Publish [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) to the command topic. Without `endpointDetails`, the reply lists the active endpoints and the names of all saved endpoints.

   ```json title="get_endpoint_config — request (contract example: Active endpoint config)"
   {
     "command": "get_endpoint_config",
     "requestId": "abc123"
   }
   ```

   To read one endpoint, name it in `endpointDetails`:

   ```json title="get_endpoint_config — request (contract example: Specific endpoint config)"
   {
     "command": "get_endpoint_config",
     "requestId": "def456",
     "endpointDetails": {
       "endpointName": "ctrl"
     }
   }
   ```

2. Check that `response.code` is `0`.
3. Read `endpointResponse.activeEndpoints.epConfig[]` for the configuration of each active endpoint, and `endpointResponse.savedEndpoints.epNames[]` for the name of every saved endpoint, active or not. A name that appears in `epNames` but not in `activeEndpoints` is saved and inactive.

`get_endpoint_config` is safe to send again. It can return code `3` when the reader cannot gather the information at that moment; retry after a short delay.

A read-back lists publish topics from slot 0 upward. When it shows fewer than three, it does not say which slots are unused, so re-send the full `publishTopics` array whenever you change one entry.

## Add an Endpoint {#add}

1. Choose a name of at most 15 characters that no saved endpoint uses. Check `savedEndpoints.epNames[]` from the previous section.
2. Set the publish topics by position. The reader decides what to publish on each entry by its index, never by the topic text:

   | `epType` | `subscribeTopics[0]` | `publishTopics[0]` | `publishTopics[1]` | `publishTopics[2]` |
   |---|---|---|---|---|
   | `MGMT`, `MDM` | Commands (required) | Replies (required) | Events (recommended) | Last Will and `mqttConnEVT` (recommended) |
   | `CTRL` | Control commands (required) | Control replies (required) | Stored, not used for events | Last Will and `mqttConnEVT` (optional) |
   | `MGMT_EVT` | Required; events are currently published here | Not used | Not used | Last Will (optional) |
   | `DATA1` | Not used | Not used for tag data | Tag data (required) | Last Will (optional) |

   Write only the middle segment in each `topic`. The reader adds the tenant ID in front and its serial number at the end. At most three publish topics and one subscribe topic are accepted.

3. Publish [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) with `operation: "add"`. This example adds a management endpoint over TLS:

   ```json title="config_endpoint — request (illustrative: Add MGMT endpoint for MQTT TLS; addresses replaced with fictional ones)"
   {
     "command": "config_endpoint",
     "requestId": "1233",
     "epConfig": {
       "operation": "add",
       "configuration": {
         "endpointName": "mgmt_tls",
         "epType": "MGMT",
         "protocol": "MQTT_TLS",
         "activate": true,
         "url": "broker.example.com",
         "port": 8883,
         "verificationType": "VERIFY_HOST_AND_PEER",
         "qosCommon": 1,
         "tenantId": "ZEBRA",
         "mqttParams": {
           "keepAlive": 300,
           "cleanSession": true,
           "reconnectDelayMin": 5,
           "reconnectDelayMax": 60,
           "publishTopics": [
             {
               "topic": "MGMT/clients/resp",
               "qos": 1,
               "retain": false
             },
             {
               "topic": "MGMT/clients/event",
               "qos": 1,
               "retain": false
             },
             {
               "topic": "MGMT/clients/rfid",
               "qos": 0,
               "retain": true
             }
           ],
           "subscribeTopics": [
             {
               "topic": "MGMT/clients/cmnd",
               "qos": 0,
               "retain": false
             }
           ]
         },
         "securityParams": {
           "format": "PEM",
           "caCertificateFile": "mqtt_ca_cert",
           "clientCert": "mqtt_client_cert",
           "clientKey": "mqtt_client_key"
         }
       }
     }
   }
   ```

   A data endpoint needs a filler topic in slot 0 so that its tag-data topic lands in slot 1:

   ```json title="config_endpoint — request (illustrative; filler topic added)"
   {
     "command": "config_endpoint",
     "requestId": "abc123",
     "epConfig": {
       "operation": "add",
       "configuration": {
         "endpointName": "dataEP",
         "epType": "DATA1",
         "protocol": "MQTT",
         "activate": true,
         "url": "broker.example.com",
         "verificationType": "VERIFY_NONE",
         "port": 1883,
         "qosCommon": 1,
         "tenantId": "zebra",
         "mqttParams": {
           "keepAlive": 300,
           "cleanSession": true,
           "reconnectDelayMin": 50,
           "reconnectDelayMax": 500,
           "username": "********",
           "password": "XXXXXXXX",
           "publishTopics": [
             {
               "topic": "DATA/clients/unused",
               "qos": 0,
               "retain": false
             },
             {
               "topic": "DATA/clients/data1event",
               "qos": 1,
               "retain": false
             }
           ]
         }
       }
     }
   }
   ```

   Replace the masked credentials with your own, and never commit real ones.

4. Check the reply. A successful add returns code `0`:

   ```json title="config_endpoint — response (contract example: Endpoint configured)"
   {
     "command": "config_endpoint",
     "requestId": "abc123",
     "apiVersion": "V1.1",
     "response": {
       "code": 0,
       "description": "Success"
     }
   }
   ```

Send `activate` explicitly; its default is `false`. Settings you can leave out take these defaults: `qosCommon` is `0`, and `tenantId` is empty. Keep `protocol` and `port` consistent: the reader does not cross-check them, and a plain `MQTT` connection to port `8883` fails to connect.

## Stage an Endpoint, Then Activate It {#stage-and-activate}

An endpoint added with `activate: false` is saved but not connected. Staging lets you check a new broker configuration before any traffic depends on it:

1. Add the endpoint with `activate: false`.
2. Confirm with `get_endpoint_config` that its name is in `savedEndpoints.epNames[]`.
3. Subscribe to the endpoint's connection-state topic, its `publishTopics[2]`.
4. Send an `update` that sets `activate: true`. The reader checks the parameters and, if they are valid, connects to the endpoint without a reboot.
5. Confirm the connection. The reader publishes a `CONNECTED` `mqttConnEVT` on the endpoint's `publishTopics[2]`. See [Monitor Reader Connectivity](/guides/operate-and-monitor/monitor-reader-connectivity).

## Update an Endpoint {#update}

Send `operation: "update"` with every required configuration field, using the current values from `get_endpoint_config` and changing only the intended settings:

```json title="config_endpoint — request (illustrative: Update endpoint)"
{
  "command": "config_endpoint",
  "requestId": "1233",
  "epConfig": {
    "operation": "update",
    "configuration": {
      "endpointName": "mgmt_tls",
      "epType": "MGMT",
      "protocol": "MQTT_TLS",
      "activate": true,
      "url": "broker.example.com",
      "verificationType": "VERIFY_HOST_AND_PEER",
      "port": 8883,
      "tenantId": "ZEBRA"
    }
  }
}
```

The reader refuses to modify an active endpoint and returns code `35`. Deactivate it first. Send the update for an endpoint over a different active management endpoint: deactivating the endpoint that carries your commands ends your connection to the reader.

## Delete an Endpoint {#delete}

Send `operation: "delete"` with the endpoint's name, type and every required configuration field, using its current read-back values:

```json title="config_endpoint — request (illustrative: Delete endpoint)"
{
  "command": "config_endpoint",
  "requestId": "1233",
  "epConfig": {
    "operation": "delete",
    "configuration": {
      "endpointName": "mgmt_tst",
      "epType": "MDM",
      "protocol": "MQTT",
      "activate": false,
      "url": "broker.example.com",
      "verificationType": "VERIFY_NONE",
      "port": 1883
    }
  }
}
```

## Handle Refusals {#refusals}

Besides `0` and the catch-all `101`, the contract scopes these codes to `config_endpoint`:

| Code | Meaning | What to do |
|---|---|---|
| `10` | Configuration already exists | Use a different name, or delete the existing endpoint first |
| `23` | Invalid enum value | Correct the value from the enum on the reference page |
| `25` | Max 3 publish topics exceeded | Send at most three publish topics |
| `26` | Max 1 subscribe topic exceeded | Send one subscribe topic |
| `27` | Invalid tenant ID length | Use a tenant ID of at most 48 characters |
| `33` | Endpoint already configured | Modify the existing endpoint instead of adding it again |
| `35` | Can't modify an active endpoint | Deactivate the endpoint, then update it |

`config_endpoint` is not safe to send twice. The reader executes every copy it receives, and a repeated `add` is refused with code `10` or `33`. A refusal after a retry can therefore mean that your first request succeeded; read the configuration back before you act on it. See [Retry Commands Safely](/guides/build-your-integration/retry-commands-safely).

## If the Reader Loses Its Connection {#rollback}

An endpoint change that points the reader's only management connection at an unreachable broker leaves no MQTT path to undo it. Connect the reader to 123RFID Desktop over USB-C and restore the previous endpoint, as in [Bootstrap a Reader with 123RFID Desktop](/guides/manage-your-reader/bootstrap-reader). Try endpoint changes on one reader before you roll them out to a fleet.
