A reader stores Wi-Fi profiles, one per network, and you manage them over MQTT with [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi), [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi) and [`delete_wifi_profile`](/api-reference/mqtt/mgmt/delete-wifi-profile). [`get_eth`](/api-reference/mqtt/mgmt/get-eth) reads the Ethernet interface; the MQTT API has no command that changes it.

## Before You Begin {#before-you-begin}

- The reader has a working MQTT connection. The first Wi-Fi profile cannot arrive over MQTT, because the reader needs a network to reach the broker; it is set with 123RFID Desktop in [Bootstrap a Reader with 123RFID Desktop](/guides/manage-your-reader/bootstrap-reader).
- Your application is subscribed to the management endpoint's response topic, for example `<tenantId>/MGMT/clients/resp/<deviceSerialNumber>`, and publishes commands to `<tenantId>/MGMT/clients/cmnd/<deviceSerialNumber>`. Use the middle segments your endpoint is configured with.
- For an Enterprise profile, the certificates it names are installed with type `wifi`. See [Install and Manage Certificates](/guides/manage-your-reader/install-and-manage-certificates).

:::caution[Changing the active network can cut your connection]
The Wi-Fi connection is what carries the reader's MQTT session. A profile that switches the reader to a network without a route to your broker disconnects it, and the fix then needs 123RFID Desktop. Save a new profile with `connect: false` first, and switch to it only when you know the new network reaches the broker.
:::

## Read the Saved Profiles {#read}

1. Publish `get_wifi`:

   ```json title="get_wifi — request (illustrative; the contract has no example)"
   {
     "command": "get_wifi",
     "requestId": "abc123"
   }
   ```

2. Check that `response.code` is `0`. Code `3` means the reader could not gather the information at that moment; retry after a short delay.
3. Read `wifiProfiles.wifiConfig[]`. Each entry's `interfaceDetails.accessPoint` gives the `essid`, `status`, `securityType` and `isPreferred` of a profile, and the connected profile also carries `ipv4Configuration`.

```json title="get_wifi — response (adapted from contract example: WPA2 Personal connection; addresses replaced with fictional ones)"
{
  "command": "get_wifi",
  "requestId": "abc123",
  "apiVersion": "V1.1",
  "wifiProfiles": {
    "wifiConfig": [
      {
        "interfaceDetails": {
          "interfaceName": "wlan0",
          "status": "Enabled",
          "hostname": "RFD40-211545201D0034",
          "macAddress": "00:00:5E:00:53:01",
          "accessPoint": {
            "essid": "IOT_TESTAP",
            "status": "CONNECTED",
            "securityType": "WPA2Personal",
            "isPreferred": false,
            "autoConn": false
          },
          "ipv4Configuration": {
            "ipAddress": "192.0.2.110",
            "subnetMask": "255.255.255.0",
            "gateway": "192.0.2.1",
            "enableDhcp": true,
            "dnsServer": "192.0.2.1",
            "domainName": "zebra.com"
          },
          "securityDetails": {
            "WPA2Personal": {
              "password": "XXXXXXXX"
            }
          }
        }
      }
    ]
  },
  "response": {
    "code": 0,
    "description": "Success"
  }
}
```

When the Wi-Fi interface is disabled, the reply carries a single `wifiConfig.interfaceDetails` object with `status: "Disabled"` instead of `wifiProfiles`. Read both shapes.

## Create a Profile {#create}

Use `operation: "CREATE"` for a network the reader has no profile for. `operation` and `accessPoint` are required, and `accessPoint` requires `essid`. When `enableSecurity` is `true`, `security` must carry both `securityType` and the matching member of `securityDetails`.

```json title="set_wifi — request (adapted from contract example: Create WPA2 personal; password masked)"
{
  "command": "set_wifi",
  "requestId": "abc123",
  "wifiConfig": {
    "interfaceName": "wlan0",
    "enableInterface": true,
    "operation": "CREATE",
    "accessPoint": {
      "connect": false,
      "isPreferred": false,
      "autoConn": true,
      "essid": "TestAP1",
      "enableSecurity": true,
      "security": {
        "securityType": "WPA2Personal",
        "securityDetails": {
          "WPA2Personal": {
            "password": "XXXXXXXX"
          }
        }
      }
    }
  }
}
```

The contract example still sends `autoConn`, which is deprecated and will be removed; leave it out of new requests. Replace `XXXXXXXX` with the network's pre-shared key, which is 8 to 63 characters.

| `accessPoint` member | Effect |
|---|---|
| `connect` | `true` disconnects the current profile and connects to this one; `false` only saves it |
| `isPreferred` | `true` makes this the profile the reader always connects to when it is available. Defaults to `false` |
| `enableSecurity` | `true` requires `security`. Whether an open-network profile is set with `enableSecurity: false`, with `securityType: Open`, or with both, and whether `set_wifi` accepts one at all, is not confirmed in the available sources. `get_wifi` can report `securityType: Open` |
| `ipv4Configuration` | With `enableDhcp: true`, the address, mask, gateway, DNS server and domain come from the DHCP server. The command's source states that static IPv4 and IPv6 are not available in the current API version |

`securityType` selects which member of `securityDetails` you send: `WPA2Personal` or `WPA3Personal` with a `password`, or `WPA2Enterprise` or `WPA3Enterprise` with the Enterprise members below.

A successful request returns code `0` and no copy of the profile:

```json title="set_wifi — response (contract example: Wifi configuration set)"
{
  "command": "set_wifi",
  "requestId": "abc123",
  "apiVersion": "V1.1",
  "response": {
    "code": 0,
    "description": "Success"
  }
}
```

## Create an Enterprise Profile {#create-enterprise}

An Enterprise profile names installed certificates by their logical names in `certificate`, a list of `{key, value}` entries. `key` is `ca_cert`, `client_cert`, `client_key` or `cert_key_password`.

| `authentication` | Credentials | `innerAuthentication` |
|---|---|---|
| `tls` | `ca_cert`, `client_cert` and `client_key` certificates | Omit it |
| `ttls` | `identity` and `password` or `passphrase`, usually with a `ca_cert` | `mschapv2`, the default when omitted |
| `peap` | `identity` and `password` or `passphrase`, usually with a `ca_cert` | `mschapv2`, the default when omitted |

`protocol` sets the cipher suite. `WPA2Enterprise` has one value, `WPA2_Enterprise_CCMP`. `WPA3Enterprise` has five: `WPA3_Enterprise_CCMP`, `WPA3_Enterprise_CCMP_256`, `WPA3_Enterprise_GCMP_128`, `WPA3_Enterprise_GCMP_256_SHA256` and `WPA3_Enterprise_GCMP_256_SUITEB_192`.

```json title="set_wifi — request (adapted from contract example: Create WPA2 enterprise PEAP; password masked)"
{
  "command": "set_wifi",
  "requestId": "abc123",
  "wifiConfig": {
    "interfaceName": "wlan0",
    "enableInterface": true,
    "operation": "CREATE",
    "accessPoint": {
      "connect": false,
      "isPreferred": false,
      "autoConn": true,
      "essid": "Vulcan_WPA2_24_5_ENT_SHA256",
      "enableSecurity": true,
      "security": {
        "securityType": "WPA2Enterprise",
        "securityDetails": {
          "WPA2Enterprise": {
            "authentication": "peap",
            "innerAuthentication": "mschapv2",
            "identity": "steve",
            "anonymousIdentity": "none",
            "password": "XXXXXXXX",
            "certificate": [
              {
                "key": "ca_cert",
                "value": "wifi_ca_cert"
              }
            ],
            "protocol": "WPA2_Enterprise_CCMP"
          }
        }
      }
    }
  }
}
```

The contract does not say how `passphrase` differs from `password`. The reference page for [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi) has the TLS and TTLS examples and the WPA3 variants.

## Modify a Profile {#modify}

Use `operation: "MODIFY"` for a network the reader already has a profile for. The `essid` selects the profile. This example makes a saved profile the preferred one without changing its credentials:

```json title="set_wifi — request (contract example: Set preferred AP)"
{
  "command": "set_wifi",
  "requestId": "abc123",
  "wifiConfig": {
    "operation": "MODIFY",
    "accessPoint": {
      "isPreferred": true,
      "essid": "TestAP1"
    }
  }
}
```

When `interfaceName` is left out, as here, the reader applies the change to its single Wi-Fi interface.

## Delete a Profile {#delete}

```json title="delete_wifi_profile — request (contract example: Delete wifi profile)"
{
  "command": "delete_wifi_profile",
  "requestId": "abc123",
  "wifiProfileInfo": {
    "essid": "TestAP2"
  }
}
```

The reader refuses to delete the profile it is connected to and returns code `16`. Connect to a different profile first.

## Confirm the Change {#confirm}

A code `0` reply means the reader accepted the profile, not that it joined the network. Send `get_wifi` again and check the profile you changed:

- `accessPoint.status` is `CONNECTED` when the reader has joined that network.
- `ipv4Configuration.ipAddress` holds an address once DHCP has assigned one.

A joined network with an address still does not prove that the broker is reachable. If the MQTT session does not come up, see [Network and Connectivity](/guides/diagnose-and-recover/diagnose-by-system-area/network-and-connectivity).

## Handle Refusals {#response-codes}

| Code | Meaning | Returned by | What to do |
|---|---|---|---|
| `2` | Invalid payload | `set_wifi`, `delete_wifi_profile` | Correct the payload against the command's schema |
| `3` | Not able to retrieve information | `get_wifi`, `get_eth` | Retry after a short delay |
| `15` | SSID not found | `set_wifi`, `delete_wifi_profile` | Check the ESSID, or use `CREATE` for a new network |
| `16` | Cannot delete active SSID | `delete_wifi_profile` | Connect to a different profile, then delete |
| `17` | SSID missed | `set_wifi`, `delete_wifi_profile` | Include the ESSID |
| `18` | SSID already exist | `set_wifi` | Use `MODIFY`, or delete the profile first |
| `19` | SSID count overflow | `set_wifi` | Delete an unused profile. The contract does not state the maximum number of profiles |
| `20` | Wifi is not supported | `set_wifi` | The reader has no Wi-Fi interface |
| `23` | Invalid enum value | `set_wifi` | Correct the value from the enum on the reference page |

`set_wifi` is not safe to send twice: a repeated `CREATE` is refused with code `18`. A code `18` after a retry can mean that your first request succeeded, so read the profiles back before you act on it.

## Read the Ethernet Interface {#ethernet}

The contract describes the reader connecting over Wi-Fi and Ethernet. Ethernet is read-only over MQTT: `get_eth` reports the interface, and no command changes it. Which reader hardware exposes an Ethernet interface is not specified in the available sources.

```json title="get_eth — request (illustrative; the contract has no example)"
{
  "command": "get_eth",
  "requestId": "abc123"
}
```

```json title="get_eth — response (adapted from contract example: Ethernet config info; addresses replaced with fictional ones)"
{
  "command": "get_eth",
  "requestId": "abc123",
  "apiVersion": "V1.1",
  "ethConfig": {
    "interfaceDetails": {
      "interfaceName": "eth0",
      "status": "Enabled",
      "hostname": "RFD40-211545201D0020",
      "macAddress": "00:00:5E:00:53:02",
      "linkStatus": {
        "status": "Connected",
        "linkSpeed": "100Mbps"
      },
      "ipv4Configuration": {
        "ipAddress": "192.0.2.101",
        "subnetMask": "255.255.255.0",
        "gateway": "192.0.2.1",
        "enableDhcp": true,
        "dnsServer": "0.0.0.0",
        "domainName": "zebra.com"
      }
    }
  },
  "response": {
    "code": 0,
    "description": "Success"
  }
}
```

When the interface is disabled, `interfaceDetails` carries only `interfaceName` and `status: "Disabled"`, and the reply is still code `0`:

```json title="get_eth — response (contract example: Ethernet interface disabled)"
{
  "command": "get_eth",
  "requestId": "abc123",
  "apiVersion": "V1.1",
  "ethConfig": {
    "interfaceDetails": {
      "interfaceName": "eth0",
      "status": "Disabled"
    }
  },
  "response": {
    "code": 0,
    "description": "Success"
  }
}
```

The reader reports interface and link states in more than one letter case, for example `Enabled` and `ENABLED`, or `Connected` and `CONNECTED`. Compare them without regard to case.
