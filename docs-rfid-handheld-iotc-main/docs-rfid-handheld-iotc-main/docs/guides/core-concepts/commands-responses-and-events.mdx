Every message between a reader and your application belongs to one of three flows. Telling them apart tells you which topic to subscribe to, what the message looks like, and how to handle it.

| Flow | Who publishes | Paired by | QoS | Reference |
|---|---|---|---|---|
| Command and reply | Your application publishes the command; the reader publishes one reply | `requestId` | 1 | [Message Envelopes and Correlation](/api-reference/mqtt/protocol-reference/message-envelope) |
| Events | The reader | Nothing | `alerts` 1; `heartBeatEVT` and `mqttConnEVT` 0 | [Events](/api-reference/mqtt/events) |
| Tag data | The reader, during an inventory | Nothing | Configurable per topic; 0 by default | [`dataEVT`](/api-reference/mqtt/data/tag-data-event) |

## Flow 1: Command and Reply {#command-and-reply}

Your application publishes a command to the reader's command topic, for example `<tenantId>/MGMT/clients/cmnd/<serial>`. The reader publishes its reply on the response topic, `<tenantId>/MGMT/clients/resp/<serial>`, and echoes your `requestId` in it. Replies arrive out of order and interleaved with events, so the `requestId` is the only thing that pairs a reply with its request.

```json title="control_operation — request (contract example: Start inventory)"
{
  "command": "control_operation",
  "requestId": "abcd1432",
  "ctrlOprPayload": {
    "controlType": "RFID",
    "operation": "START"
  }
}
```

```json title="control_operation — response (contract example: Control operation success)"
{
  "command": "control_operation",
  "requestId": "abc123",
  "apiVersion": "V1.1",
  "response": {
    "code": 0,
    "description": "Success"
  }
}
```

The outcome is `response.code`. A reply is successful when the code is `0`, or when the code is absent and the description is `"Success"`. Except for the [documented firmware success reply without a code](/api-reference/mqtt/protocol-reference/message-envelope#success-omits-code), do not branch on `response.description`: it is text for people and can change between firmware builds. See [Response Codes](/api-reference/mqtt/response-codes).

Three things about this flow surprise people coming from HTTP:

- **There is no timeout.** The contract specifies none for any command; choose your own.
- **Repeats are not suppressed.** A command can arrive twice at QoS 1, and the reader executes every copy. For a configuration command, the last copy to arrive takes effect. Each command's reference page says whether sending it twice is safe. See [Retry Commands Safely](/guides/build-your-integration/retry-commands-safely).
- **Some commands finish later.** [`set_os`](/api-reference/mqtt/mgmt/set-os), [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate) and [`reboot`](/api-reference/mqtt/mgmt/reboot) reply with code `1`, which means the reader accepted the request, not that it succeeded. `set_os` and `install_certificate` report the outcome later in an `alerts` event. `reboot` has no outcome event: the next `CONNECTED` `mqttConnEVT` shows that a new session was established, though a network reconnect produces the same message. See [Track Asynchronous Commands](/guides/build-your-integration/track-asynchronous-commands).

## Flow 2: Events {#events}

The reader publishes events on its own: [`heartBeatEVT`](/api-reference/mqtt/events/heartbeat-event) at an interval, [`alerts`](/api-reference/mqtt/events/alerts-event) when a condition changes, and [`mqttConnEVT`](/api-reference/mqtt/events/mqtt-connection-event) when a session starts or is lost. Events carry no `requestId` and no `response` object, and no field names their kind: tell them apart by the fields they must carry. `alerts` and `heartBeatEVT` arrive on the event topic, for example `<tenantId>/MGMT/clients/event/<serial>`; `mqttConnEVT` arrives on the connection-state topic, `<tenantId>/MGMT/clients/rfid/<serial>`.

```json title="heartBeatEVT — event (contract example: Heartbeat alert received)"
{
  "eventName": "heartbeat",
  "timestamp": "2019-08-24T14:15:22Z",
  "eventNumber": 120,
  "data": {
    "inventoryStatus": {
      "rfidStatus": "INPROGRESS",
      "tagCount": 45,
      "scanCount": 128
    },
    "batteryAlert": {
      "status": "HIGH",
      "stateOfHealth": "GOOD",
      "chargePercentage": 85
    }
  }
}
```

Events are not retained. Subscribe before the event can happen, because one published before your subscription is active is not delivered later. Which events the reader publishes is set with [`config_events`](/api-reference/mqtt/mgmt/config-events); see [What to Monitor and Why](/guides/operate-and-monitor/what-to-monitor-and-why).

## Flow 3: Tag Data {#tag-data}

While an inventory runs, the reader publishes [`dataEVT`](/api-reference/mqtt/data/tag-data-event). On a dedicated data endpoint it arrives on `<tenantId>/DATA/clients/data1event/<serial>`, the `DATA1` topic (`DATA2` is currently not supported). Each event can carry several tag records. Firmware limits a tag-data event to 6144 bytes, not to a number of tags, and the endpoint's `batching` settings control how reads are grouped.

```json title="dataEVT — event (contract example: Tag data with additional details)"
{
  "type": "BALANCED_PERFORMANCE",
  "timestamp": "2026-06-16T06:14:26.782Z",
  "data": {
    "tagData": [
      {
        "EPCid": "AAAABBBB11112222CCCCDDDD",
        "EPC": "D98A3000AAAABBBB11112222CCCCDDDD",
        "TID": "E2003412012DFA000FF5D1E4031D0136000D5FFBFFFFDC60",
        "channel": 9216,
        "eventNum": 91,
        "peakRssi": -62,
        "phase": 64,
        "seenCount": 256,
        "MAC": "AC:3F:A4:00:2B:15",
        "HOSTNAME": "RFD40-211545201D0034"
      },
      {
        "EPCid": "CCCCCCCCA5050077AB3800CC",
        "EPC": "3BA23000CCCCCCCCA5050077AB3800CC",
        "TID": "E28011B02000A0CC59C003BD000000000000",
        "channel": 9472,
        "eventNum": 92,
        "peakRssi": -76,
        "phase": -171,
        "seenCount": 256,
        "MAC": "AC:3F:A4:00:2B:15",
        "HOSTNAME": "RFD40-211545201D0034"
      }
    ]
  }
}
```

`type` names the operating-mode profile that was active. Which metadata fields a tag record carries depends on the metadata flags set with [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode), so treat every field except `eventNum` as optional.

`dataEVT` is published at the QoS set on its topic, 0 or 1, and is not retained. The contract describes the stream as a statistical view of the tag population, not a guaranteed log of every read. See [The Tag Data Stream](/guides/core-concepts/the-tag-data-stream).

## Which Topic to Subscribe To {#which-topic}

| Direction | Your application | The reader |
|---|---|---|
| Commands | Publishes | Subscribes |
| Replies | Subscribes | Publishes |
| Events | Subscribes | Publishes |
| Tag data | Subscribes | Publishes |

Every topic is `<tenantId>/<middle segment>/<deviceSerialNumber>`, and the middle segments come from the endpoint's configuration. See [Endpoints, Topics, and Channels](/guides/core-concepts/endpoints-topics-and-channels).
