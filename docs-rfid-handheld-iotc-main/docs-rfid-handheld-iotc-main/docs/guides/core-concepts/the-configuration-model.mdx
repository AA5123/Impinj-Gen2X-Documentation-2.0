A reader's configuration is not one document. It is a set of separate domains, each changed and read by its own commands, and each with its own rules for updates, refusals and reboots. This page explains those rules. The commands themselves are in the [MQTT API](/api-reference/mqtt) reference.

## Configuration Is Split by Domain {#domains}

Each domain has its own commands. No command in the MQTT API reads or writes a reader's whole configuration at once, so a complete picture of a reader comes from reading each domain in turn.

| Domain | Change it with | Read it with |
|---|---|---|
| MQTT endpoints | [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) | [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) |
| Event reporting | [`config_events`](/api-reference/mqtt/mgmt/config-events) | Not specified in the available sources |
| Wi-Fi profiles | [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi), [`delete_wifi_profile`](/api-reference/mqtt/mgmt/delete-wifi-profile) | [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi) |
| Certificates | [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate), [`delete_certificate`](/api-reference/mqtt/mgmt/delete-certificate) | [`get_installed_certificates`](/api-reference/mqtt/mgmt/get-installed-certificates) |
| Operating mode | [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) | [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode) |
| Post-filters | [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter) | [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter) |
| Firmware | [`set_os`](/api-reference/mqtt/mgmt/set-os) | [`get_version`](/api-reference/mqtt/mgmt/get-version) |

`config_events` has no read command of its own. Its settings show in the `eventConfiguration` block of each active endpoint in the [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) read-back, but the contract also describes that block as a separate, per-endpoint setting and does not say which of the two wins. Keep a record of what you sent.

## Domains You Can Only Read {#read-only-domains}

Some of what a reader reports cannot be changed over MQTT:

| Domain | Read it with | Notes |
|---|---|---|
| Identity and firmware versions | [`get_version`](/api-reference/mqtt/mgmt/get-version) | Firmware changes only through `set_os` |
| Runtime status | [`get_status`](/api-reference/mqtt/mgmt/get-status) | Power source, battery, radio activity and connection, system time |
| Regulatory region | [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region) | No MQTT command sets the region; it is set with [123RFID Desktop](/resources/setup-tools) or 123RFID Mobile |
| Ethernet | [`get_eth`](/api-reference/mqtt/mgmt/get-eth) | The MQTT API has no command that changes Ethernet settings |

## Partial Updates {#partial-updates}

Most configuration commands change part of a domain and leave the rest alone:

- **Operating mode.** `set_operating_mode` accepts partial updates: every member of `operatingModes` is optional, and one of the contract's examples sets only the radio start and stop conditions.
- **Event reporting.** Every member of `eventConfiguration` is optional, and an empty object is legal and changes nothing.
- **Endpoints, Wi-Fi profiles and post-filters.** Each request names an operation on one item: `add`, `update` or `delete` for an endpoint; `CREATE` or `MODIFY` for a Wi-Fi profile; `ADD`, `DELETE` or `MODIFY` for a post-filter rule.

The operation vocabularies differ in case from one command to another. Send each one exactly as its reference page shows it.

## The Last Write Wins {#last-write-wins}

The reader keeps no request history. Every copy of a command that arrives is executed, and for a configuration command the last copy to arrive is the one that takes effect. Two applications that configure the same reader therefore overwrite each other's settings, and the reader does not warn either of them. Give one application ownership of each domain. See [Retry Commands Safely](/guides/build-your-integration/retry-commands-safely).

## Refusals While the Reader Is Busy {#refusals}

Some changes are refused while the reader is doing something that conflicts with them. The refusal is a status code, and the contract marks each of these as one where a later retry may succeed:

| Code | Meaning | Returned by | Clear the condition by |
|---|---|---|---|
| `4` | Firmware update in progress | `set_os`, and other commands sent during an update | Waiting for the running update to finish |
| `5` | Can't reboot device, inventory in progress | `reboot` | Stopping the inventory with `control_operation` |
| `11` | Inventory in progress | `set_operating_mode`, `control_operation` | Stopping the inventory before changing the mode |
| `16` | Cannot delete active SSID | `delete_wifi_profile` | Connecting to a different network first |
| `35` | Can't modify an active endpoint | `config_endpoint` | Deactivating the endpoint first |

Check the reader's state before a change that can be refused. [`get_status`](/api-reference/mqtt/mgmt/get-status) reports `radioActivity`, which shows whether the radio is running. See [Response Codes](/api-reference/mqtt/response-codes).

## What a Reboot Changes {#reboots}

A reboot affects domains differently:

- **Event reporting needs one.** A change made with `config_events` takes effect only after the reader reboots. See [Configure Event Reporting](/guides/operate-and-monitor/configure-event-reporting).
- **The operating mode does not survive one.** The contract states that on reboot the settings made with `set_operating_mode` are lost and the reader returns to its default operating mode. `get_operating_mode` returns the running mode, and nothing in its reply shows whether that mode would survive a reboot. Re-apply your operating mode after every reboot.
- **Endpoint changes don't need one.** When you activate an endpoint, the reader checks its parameters and, if they are valid, connects to it without a reboot. Saved and active endpoints survive a reboot. See [Changing an Endpoint](/api-reference/mqtt/protocol-reference/connection-and-session#changing-an-endpoint).
- **Other domains.** Whether Wi-Fi profiles, certificates and post-filters survive a reboot is not specified in the available sources.

`reboot` itself replies with code `1` and reports no outcome event. The next `CONNECTED` `mqttConnEVT` shows that a new session was established, but on its own it does not show that a restart occurred. See [Update Firmware and Restart the Reader](/guides/manage-your-reader/update-firmware-and-restart).
