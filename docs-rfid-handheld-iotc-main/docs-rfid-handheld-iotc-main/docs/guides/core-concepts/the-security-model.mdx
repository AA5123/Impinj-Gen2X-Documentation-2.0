A reader's connection to your broker is protected in several independent ways, and each one defends against something different. This page explains what each protection does and how the reader's certificates fit in. The procedures are in [Install and Manage Certificates](/guides/manage-your-reader/install-and-manage-certificates) and [Secure an Endpoint with TLS and Client Certificates](/guides/manage-your-reader/secure-an-endpoint).

## Four Protections {#four-protections}

| Protection | What it defends against | How it is set |
|---|---|---|
| **Encryption** | Someone reading traffic on the network | The endpoint's `protocol` is `MQTT_TLS` rather than `MQTT` |
| **Broker verification** | A server pretending to be your broker | The endpoint's `verificationType`, checked against an installed CA certificate |
| **Reader identity** | An unauthorized client connecting as your reader | A username and password in the MQTT CONNECT packet, or a client certificate for mutual TLS |
| **Tenant separation** | One tenant's applications reading another's topics | The endpoint's `tenantId`, which begins every topic, together with your broker's access rules |

The protections combine; none replaces another. TLS without broker verification encrypts the traffic but does not prove who is at the other end. Credentials without TLS travel in the clear: the contract notes that the username and password in the CONNECT packet are plaintext unless the connection is TLS-protected, and recommends port 8883 with TLS on any untrusted network.

## Verifying the Broker {#verifying-the-broker}

`verificationType` sets how far the reader checks the broker's certificate:

| Value | The reader checks |
|---|---|
| `VERIFY_HOST_AND_PEER` | The certificate chain and that the certificate matches the broker host |
| `VERIFY_NONE` | Nothing: the connection is encrypted, but the broker is not authenticated |

Do not use `VERIFY_NONE` in production: the contract states that disabling verification must not be used there. The CA certificate the reader verifies against is named in the endpoint's `securityParams.caCertificateFile`. See [TLS and Authentication](/api-reference/mqtt/protocol-reference/tls-and-authentication).

## Certificates Referred to by Name {#certificates-by-name}

Certificates are installed on the reader with [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate), and configuration refers to them by name rather than carrying their content: an endpoint's `securityParams` names its `caCertificateFile`, `clientCert` and `clientKey`, and an Enterprise Wi-Fi profile names its certificates in `certificate`. The contract does not state how those names relate to the `name` given at install; see [Install and Manage Certificates](/guides/manage-your-reader/install-and-manage-certificates#list).

The certificate `type` says where a certificate is used:

| `type` | Used for |
|---|---|
| `mqtt` | The MQTT broker connection |
| `wifi` | 802.1X Wi-Fi authentication |
| `filestore` | Authenticating downloads |
| `client` | A client identity certificate the reader presents |
| `server` | A server certificate or trust anchor the reader validates against |

The reader supports PEM only. Private keys must be PKCS1-encoded, and each component is limited to 4 KB.

Certificate content reaches the reader in one of two ways, set by `certSource`: `HTTP` (the default), where the reader downloads it from URLs you give, or `DIRECT`, where the content is inline in the command.

## Knowing an Install Succeeded {#install-outcome}

`install_certificate` finishes after it replies. It acknowledges with code `1`, and reports the outcome later as an `alerts` event with `id: FILE_DOWNLOAD`, whose `downloadInfo` carries `fileType: FILE_TYPE_CERT` and a `status` of `DOWNLOAD SUCCESS`, `DOWNLOAD FAIL`, `SAVE SUCCESS` or `SAVE FAIL`. Subscribe to the event topic before you send the command. See [Track Asynchronous Commands](/guides/build-your-integration/track-asynchronous-commands).

## Rotation and Expiry {#rotation}

Because configuration points at a name rather than at content, a certificate can in principle be replaced by installing a new one, pointing the configuration at it, confirming that the reader reconnects, and only then deleting the old one. Whether a second certificate of the same type can sit beside the first is not specified in the available sources, so confirm it before you depend on it. No event warns of an approaching expiry: `get_installed_certificates` reports each certificate's `validTill`. See [Rotate Certificates](/guides/manage-your-reader/install-and-manage-certificates#the-logical-name-rotation-pattern).
