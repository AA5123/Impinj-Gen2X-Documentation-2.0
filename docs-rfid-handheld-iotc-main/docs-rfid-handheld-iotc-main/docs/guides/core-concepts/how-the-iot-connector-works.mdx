The IoT Connector is the firmware on RFD40 and RFD90 readers that lets an application manage the reader, run RFID inventories and receive tag data over MQTT. This page explains who takes part in a deployment, where state lives, and the shape every message takes.

## Who Takes Part {#who-takes-part}

| Party | Role |
|---|---|
| **Reader** | The RFD40 or RFD90 hardware. It stores the configuration that tells the IoT Connector which broker to use. |
| **IoT Connector** | The firmware on the reader. For each active endpoint, it opens its own MQTT session to the broker named in that endpoint, receives commands, and publishes replies, events and tag data. |
| **Broker** | Your MQTT 3.1.1 broker. It relays messages between the reader and your applications. The API has no default broker: its address is part of the reader's endpoint configuration. |
| **Host application** | Your application that controls the reader. It publishes commands and subscribes to replies. |
| **Consuming applications** | Applications that subscribe to events and tag data. The host application can be one of them, and several consumers can subscribe to the same data topic. `DATA2` is currently not supported. |

The reader and your applications never address each other directly. Each is an MQTT client of the same broker, and the broker delivers each message to whoever subscribed to its topic.

**123RFID Desktop** enters the reader's first endpoint configuration during bootstrap. From then on, endpoints can be added and changed over MQTT with [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint). See [Bootstrap a Reader with 123RFID Desktop](/guides/manage-your-reader/bootstrap-reader).

## Where State Lives {#where-state-lives}

The reader holds its own configuration: its endpoints, Wi-Fi profiles, installed certificates, operating mode, post filters and event settings. An application learns that state by asking for it with the `get_*` commands, and learns of changes from the events the reader publishes. The MQTT API has no command that changes the reader's regulatory region; [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region) reads it.

Because the reader is the only holder of its state, an application that reconnects after an outage should read the state again rather than assume that nothing changed while it was away.

## Interfaces: MQTT and Tools {#interfaces-mqtt-and-tools}

MQTT is the only programming interface to the IoT Connector on a handheld reader. There is no REST interface. 123RFID Desktop is the tool for bootstrap; everything after that goes through the MQTT API.

Three kinds of message cross the broker:

| Kind | Direction | Paired by |
|---|---|---|
| Commands and replies | Your application publishes a command; the reader publishes one reply on the response topic | `requestId`, which the reader echoes |
| Events: `mqttConnEVT`, `heartBeatEVT`, `alerts` | The reader publishes | Nothing: an event answers no command |
| Tag data: `dataEVT` | The reader publishes during an inventory | Nothing |

## The Shape of a Command {#command-shape}

Every command is a JSON object with the command name, a `requestId` you choose, and at most one named payload object that holds the command's parameters:

| Command | Named payload object |
|---|---|
| [`config_endpoint`](/api-reference/mqtt/mgmt/config-endpoint) | `epConfig` |
| [`config_events`](/api-reference/mqtt/mgmt/config-events) | `eventConfiguration` |
| [`control_operation`](/api-reference/mqtt/ctrl/control-operation) | `ctrlOprPayload` |
| [`delete_certificate`](/api-reference/mqtt/mgmt/delete-certificate) | `certificateInfo` |
| [`delete_wifi_profile`](/api-reference/mqtt/mgmt/delete-wifi-profile) | `wifiProfileInfo` |
| [`get_endpoint_config`](/api-reference/mqtt/mgmt/get-endpoint-config) | `endpointDetails` (optional) |
| [`install_certificate`](/api-reference/mqtt/mgmt/install-certificate) | `certDetails` |
| [`set_operating_mode`](/api-reference/mqtt/ctrl/set-operating-mode) | `operatingMode` |
| [`set_os`](/api-reference/mqtt/mgmt/set-os) | `OSUpdateDetails` |
| [`set_post_filter`](/api-reference/mqtt/ctrl/set-post-filter) | `postFilterPayload` |
| [`set_wifi`](/api-reference/mqtt/mgmt/set-wifi) | `wifiConfig` |

The other commands take only `command` and `requestId`: [`get_version`](/api-reference/mqtt/mgmt/get-version), [`get_status`](/api-reference/mqtt/mgmt/get-status), [`get_current_region`](/api-reference/mqtt/mgmt/get-current-region), [`get_eth`](/api-reference/mqtt/mgmt/get-eth), [`get_wifi`](/api-reference/mqtt/mgmt/get-wifi), [`get_installed_certificates`](/api-reference/mqtt/mgmt/get-installed-certificates), [`get_operating_mode`](/api-reference/mqtt/ctrl/get-operating-mode), [`get_post_filter`](/api-reference/mqtt/ctrl/get-post-filter) and [`reboot`](/api-reference/mqtt/mgmt/reboot).

This contract example starts an RFID inventory:

```json title="control_operation — request (contract example: Start inventory)"
{
  "command": "control_operation",
  "requestId": "abcd1432",
  "ctrlOprPayload": {
    "controlType": "RFID",
    "operation": "START"
  }
}
```

The payload objects are defined exactly. The contract does not allow members it does not define, so generic wrappers such as `params`, `payload` or `requestBody` are not part of any command. Copy payloads from the examples in the [MQTT API](/api-reference/mqtt) reference, which are the contract's own.

Every reply carries `command`, `requestId` and a `response` object, and usually an `apiVersion`. The outcome is `response.code`: `0` is success, and the reader may omit the code on a successful reply. See [Message Envelopes and Correlation](/api-reference/mqtt/protocol-reference/message-envelope).
