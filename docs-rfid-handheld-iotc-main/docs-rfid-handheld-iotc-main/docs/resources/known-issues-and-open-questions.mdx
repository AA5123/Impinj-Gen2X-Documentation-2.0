These are the public entries: where firmware departs from the contract, what is declared but not supported, and what the contract does not yet specify. "Not yet specified" means: do not rely on the behavior until it is.

## Firmware Behavior {#firmware-behavior}

| Issue | What to do |
|---|---|
| A `MGMT_EVT` endpoint publishes its events on its subscribe topic instead of `publishTopics[1]`. The API owners record this as a firmware defect. | Subscribe to the endpoint's subscribe topic for its events, and confirm on your firmware. See [Endpoints, Topics, and Channels](/guides/core-concepts/endpoints-topics-and-channels#publish-topic-slots). |
| Certificate validity is checked against the reader's own clock. A reader whose date and time are wrong or unset can reject a valid certificate as expired or not yet valid. Zebra's release notes for `SAAFKS00-013-R05` record this. | Make sure the reader's time is right before you install certificates, and read `deviceStatus.systemTime` from [`get_status`](/api-reference/mqtt/mgmt/get-status) when an install fails for no other reason. |
| An intermittent reset when an IoT connection is established through the communication cradle. Recorded in the same release notes as a known issue. | Retry, and prefer Wi-Fi where the workflow allows it. Zebra recommends firmware `SAAFKS00-009-R00` or later when using IoT Connector with the communication cradle. |
| Zebra's release notes for `SAAFKS00-008-R00` say that the reader must reboot for Wi-Fi and endpoint configuration to take effect. On current firmware this no longer applies to endpoints: the API owners confirm that `config_endpoint` with `activate: true` connects the endpoint without a reboot. | Confirm an endpoint's connection with a `CONNECTED` [`mqttConnEVT`](/api-reference/mqtt/events/mqtt-connection-event). If a Wi-Fi change has not taken effect, plan a [`reboot`](/api-reference/mqtt/mgmt/reboot) into it. See [What a Reboot Changes](/guides/core-concepts/the-configuration-model#reboots). |

## Declared but Not Supported {#unsupported}

| Feature | Status | What to do |
|---|---|---|
| The `FAST_READ` profile | Not settled: one source says the profile is not supported, another that tag-data events are not supported with it | Use another profile. See [Choose a Performance Profile](/guides/read-tags-and-barcodes/choose-a-performance-profile) |
| The event flags `antenna`, `gpi`, `exceptions`, `ntp`, `userApp`, `temperature`, `cpuUsage`, `flashUsage`, `ramUsage`, and the four usage and temperature thresholds | Reserved: no effect on v1.1 | Do not depend on them. See [What the Event Flags Do Not Produce](/guides/operate-and-monitor/what-to-monitor-and-why#what-is-not-currently-emitted) |
| The WPA3 Enterprise protocols `WPA3_Enterprise_CCMP_256` and `WPA3_Enterprise_GCMP_128` | Zebra's release notes list both as not supported, although 123RFID Desktop offers them | Choose another WPA3 Enterprise protocol. See [Configure Wi-Fi](/guides/manage-your-reader/configure-wi-fi) |
| The link profiles `M2/640K` and `M4/640K`, added in firmware `SAAFKS00-012-R00` | The contract's `linkProfile` vocabulary has no 640K member, so they cannot be selected over MQTT | Use a declared link profile, or a named profile. See [Configure Advanced Radio Settings](/guides/read-tags-and-barcodes/configure-advanced-radio-settings#link-profiles) |

## Open Questions {#open-questions}

| Question | Not yet specified | What to do meanwhile |
|---|---|---|
| Is `mqttConnEVT` retained? | The contract declares it not retained on the channel and retained on the operation | Do not treat a `mqttConnEVT` received right after you subscribe as a new transition. See [Handle Events](/guides/build-your-integration/handle-events#retain) |
| Does every command endpoint accept every command? | Which endpoint types accept which commands | Send management commands to a management endpoint and RFID control commands to a control endpoint |
| What does batching do when only one member is set? | The behavior with only `reportingInterval` or only `maxPayloadSizePerReport` | Send both members together. See [Manage Tag Data Throughput](/guides/build-your-integration/manage-tag-data-throughput#batching) |
| Which event configuration wins: `config_events` or an endpoint's `eventConfiguration`? | Precedence between the two | Configure events with `config_events`, and keep per-endpoint settings consistent with it |
| Can tag data on a shared endpoint be post-filtered? | Whether `set_post_filter` applies to a shared endpoint | Use a dedicated `DATA1` endpoint when you need post-filters |
| What do the `inventoryStatus` counters count? | Whether they count tags or reads, and how filters and aggregation affect them | Treat a mismatch with received tag data as a signal to investigate, not proof of loss |
| Does the reader report a clean disconnect? | Whether anything is published when a session ends cleanly | Do not read the absence of a `DISCONNECTED` message as proof that the reader is connected |
